# Typed market WebSocket API

Connect to `/ws`. The GUI and external clients share this public contract. HTTP and WebSocket reads use the same `GiftOrderQuery` and `OrderReadResponse`. OpenAPI is at `/openapi.json`, AsyncAPI at `/asyncapi.json`, and interactive documentation at `/docs` and `/docs/ws`. Public market reads do not require sign-in.

## One query

Send `{"type":"request","id":"read.1","method":"orders.query","params":{"filters":{"collection_id":"tg.gift.123","currency_id":"GRAM"},"source":"asks","limit":100}}`. The result is `{type:"result",id,method:"orders.query",data,range,snapshot?}`, identical to `POST /orders/query` without the request envelope.

`source` is `asks` (default), `bids`, or `history`. Default sorts are respectively `price_asc`, `price_desc`, and `time_desc`. History accepts an optional execution `period`; other sources reject it. A query also accepts half-open `range:{start,end}`, `limit` (default and maximum 100), and `view`. The default range has two null bounds. Unknown fields are rejected.

Queries read forward in sort order within half-open key bounds. Null starts at the open head or extends to the open tail. A finite query returns up to `limit` rows and its covered range. The start is inclusive and the end is exclusive. Continue with `range.start = response.range.end`, preserving the original requested end. Stop when the returned end equals that original end; for an open-ended query this is null. Empty pages can still advance coverage. There is no `next` field. Repricing an order does not move a stored boundary. Each row has one opaque `key`. Compare keys using ordinary ASCII string order (`a < b` in JavaScript), with the same source and sort (including direction); never use locale-aware comparison. Keys contain no query fingerprint and can be reused across filters or execution periods. The supplied query still controls every returned row. Price positions use the query's currency units: reusing a key does not convert currencies or validate its former currency. Do not decode keys or reproduce ranking rules. History keys include execution-time ties. Order identity remains `(book.venue_id,id)`.

## Order payloads

HTTP queries, WebSocket queries, snapshots and upserts share the same `OrderedOrderResponse`. `book` supplies venue, collection and currency. Targets have a `kind` discriminator and flat fields:

```json
{"kind":"gift","id":"gift-id","number":42,"traits":{"model":"model-id"}}
{"kind":"criteria","models":["model-id"],"backdrops":[],"patterns":[]}
{"kind":"unsupported","code":"invalid_attributes","message":"This listing's gift details are unavailable."}
```

An order gift's collection is `book.collection_id`; standalone valuation gifts retain their own `collection_id`. Unknown gift numbers and trait IDs are omitted. Missing `market_url`, `expires_at` and `executed_at` are omitted too; executions always include `executed_at`. The dedicated `market_url` is a validated absolute HTTP(S) link without embedded credentials or control characters. Unsupported codes are typed; arbitrary source metadata is not exposed.

Protocol nulls retain meaning: `range.start`/`range.end` are always present and null denotes an open bound; An absent `snapshot` means no frozen view was retained.

## Range subscriptions

REST `POST /orders/query`, WebSocket method `orders.query`, and `orders.watch` accept the same query model. Start a watch directly; no preliminary query is needed:

```json
{"type":"orders.watch","id":"orders.1","params":{"filters":{"collection_id":"tg.gift.123","currency_id":"GRAM"},"source":"asks","range":{"start":null,"end":null},"limit":80}}
```

A watch reads up to `limit` rows (default and maximum 100) and atomically establishes the actual covered range from that read. The initial snapshot includes the covered `range`, just like a finite query. Continue from its exclusive end with `orders.query` to load more without replacing the watch. Identical resolved coverage shares a producer even while it is catching up; an exact, current range can initialize directly from that producer without another read. Each caller retains its own first snapshot before consuming coalesced shared updates, so changes during setup cannot enlarge or replace that baseline. Initialization slots and live producers are bounded separately by the live-query limit. `limit` controls initialization; later updates reconcile the complete fixed coverage, up to the 100-row live cap. Leave headroom for arrivals by initializing fewer rows, such as 80. If coverage grows beyond capacity, the operation terminates with a capacity error; restart a watch with narrower coverage. Updates never silently clip coverage.

For `source:"bids"`, the same flat query accepts `bid_match:"any"` (default) or `"all"`. Any requires an accepted value in common with each selected trait group; omitted bid conditions accept any value. All requires exactly the selected trait sets and gift-number bounds. Empty/omitted selections require absent restrictions under All: selecting models without a backdrop excludes backdrop-restricted bids. Equivalent singleton equality/set/range encodings match; set order and duplicates do not matter. Groups combine with AND. Number ranges overlap for Any and require equal bounds for All, including unbounded ends. Collection/currency/venue and bid-price filters retain their ordinary meaning. With no gift selections, Any returns all eligible bids, while All returns only unrestricted bids. Unsupported complex conditions remain visible only in unfiltered Any browsing. All matching is only valid for Bids. Matching occurs before finite pagination and live diffs; keep `bid_match` with filters when paging or reconnecting. Changing it creates a new subscription/query selection while ordering keys retain the same sort/source semantics.

```json
{"type":"orders.watch","id":"bids.1","params":{"source":"bids","bid_match":"all","filters":{"collection_id":"tg.gift.123","currency_id":"GRAM","models":["gold","silver"]},"limit":80}}
```

Bounds stay fixed as prices change, even if a boundary listing disappears. Keep the returned range rather than deriving it from first/last rows: open bounds, filtered scans and empty results carry meaningful coverage. Initialization captures data and its observation together; the producer reconciles changes since that read before waiting for new updates. Older completed reads cannot roll shared state back. There is no `navigation`, `around` operation, nested `params.query` or separate watch range. Watches require the default latest view. Inverted bounds and sort/source mismatches are rejected.

The first data frame is `{type:"orders.snapshot",id,sequence:0,data,range}`. Subsequent frames are `{type:"orders.changed",id,sequence,upserts,removed}`. Require `sequence === lastSequence + 1` for changes. Apply each batch atomically: remove both deleted and replaced identities first, then merge all upserts in `key` order. Multiple orders can exchange ranks in the same batch. Removals and upserts have disjoint identities. Removal means an order left the matching range and does not imply a sale.

Finite WebSocket order results flatten `data`, `range` and optional `snapshot` alongside `type`, `method` and `id`; there is no `data.data` wrapper. `orders.changed` frames do not repeat coverage. Frozen-view IDs belong only to finite query results.

Every `orders.snapshot` replaces the complete subscribed state, including when a dataset is replaced. Its sequence advances within that operation. Reconnect or sequence gaps require a new watch initialized from sequence zero. Watches can coalesce intermediate observations; they are current state, not a durable event journal. Live history includes late backfills within coverage.

## Frozen traversal

`view` defaults to `{kind:"latest"}` and retains no server state. Set `{kind:"snapshot"}` to pin an immutable view. The response includes a `snapshot` ID; send `view:{kind:"snapshot",id}` for subsequent reads. Follow the returned range end, keeping the original end bound, until the two ends match. A bounded scan may return short or empty data with an advancing range end; keep reading until the requested end is reached. After initialization, watched ranges always return complete coverage or an explicit capacity error. No separate history endpoint or page token is needed.

Release with `DELETE /orders/query` and `{snapshot}`. Views expire after 60 seconds idle or application restart, share bounded capacity, and require instance affinity behind a load balancer. An expired/released ID returns HTTP 409 `restart_read`; reopening at the visible key establishes a fresh baseline. Release is idempotent and an in-flight read cannot resurrect a released view.

The GUI keeps all visited listings and virtualizes mounted cards. It initializes with one 80-row watch and uses the same query model for asks, bids and history, preserving execution-period filters across paging and reconnects. Cached rows and loaded coverage are separate: a partial replacement baseline retains older rows but reopens the interval before the next cached row. Additional WebSocket queries fill unread gaps using bounded ranges; an old open-tail result does not imply that newly reopened gaps are loaded. Viewport watches stay within contiguous covered intervals below the 100-row cap. Only the active range is live; cached regions refresh on revisit. New executions and late backfills appear within watched coverage without polling or opening snapshot leases.

The latest visible anchor is remembered for reconnects without restarting healthy watches. Pagination requested while reconnecting waits for the fresh baseline. A replacement snapshot cancels an outstanding page read and preserves its intent; continuation uses current unread coverage after cancellation completes. Delayed pages cannot overwrite the current watched state. Empty filtered pages continue scanning, while retryable failures use backoff. Capacity errors prepare narrower coverage for the socket's delayed retry. Subscription state remains connecting, reconnecting or failed until a valid baseline arrives; market availability alone cannot make it Live. Explicitly paused reads use one snapshot pager; rebuilding after expiry reads through the visited tail, including cached gaps, before publishing a new view.

## Status, operations and budgets

Each connection receives a `market.status` message initially and when availability changes, for example `{type:"market.status",status:"available"}`. Status is `available` when normal market updates are available, `delayed` when previously received data can still be served, or `unavailable` when market data is not available. This message has no operation ID and does not advance order sequences. Unchanged availability does not produce duplicate status messages. A connected socket does not itself establish market availability.

Valuation reports contain `evaluated_at`, `stale` and typed strategy results with calculation evidence and static contract revisions. `stale` describes delayed inputs at evaluation time. Clients should also react to current availability: after a delay or connection loss, treat a previously displayed estimate as potentially outdated until a fresh evaluation succeeds. A response to a request started before the interruption remains potentially outdated even if it arrives after recovery. Calculation time is not an assertion about when every underlying listing changed. Status changes do not require automatically issuing valuations.

`GET /sync` is removed. Operational `/healthz` and `/readyz` remain for deployments and stay out of the consumer schema. Readiness remains successful while saved market data can be served during delays.

Operation IDs use 1..64 ASCII letters, digits, `_`, `-` or `.` and are unique while active. Rust API models use the validated `market_api::protocol::OperationId` throughout commands, operations and encoding; it still serializes as the same plain JSON string. Validation runs on command decoding, and the same type supplies ID constraints in OpenAPI and AsyncAPI. `{"type":"cancel","id":"orders.1"}` cancels without acknowledgement. A frame already being written can still arrive, so use fresh IDs for replacements and ignore retired IDs. Validation failures with a valid, unused ID return a correlated terminal `error`, so requests can fail immediately. A command that reuses an active ID returns nonterminal `command_error` and preserves the active operation. When no valid ID can be parsed, `command_error` has an empty ID. Every `error` has a nonempty operation ID; connection failures use WebSocket close frames. Method `valuation.query` shares its handler and response with HTTP.

Subscriptions return an initial snapshot, catalog version manifest or error; there is no separate connecting acknowledgement.

The GUI bounds connection handshakes to ten seconds, cancels reconnect timers when its final observer leaves, and retries persistent subscriptions with fresh wire IDs. One-shot requests are never replayed after disconnect. Terminal operation IDs are retired before callbacks run, so late frames cannot revive completed work or suppress a retry. Query updates with unchanged parameters preserve the current subscription and its sequence.

Reads, scans, range membership, encoded bytes, concurrency, outgoing queues and retained views remain bounded. All subscription setups, including portfolio watches, use the configured setup timeout and return a correlated `timed_out` error if it expires. REST order queries use the same response byte budget as WebSocket reads. Initialization and finite reads report their actual coverage and continuation. Later watch budget failures are explicit errors, never incomplete ranges presented as complete. Narrow coverage or reduce the slice size on capacity errors. Slow consumers close with code 1013; reconnect and initialize again. Cancellation, command ingress and supervision continue while data frames are written. Shutdown cancels operations and drains tracked reads and encoders.

## Catalog updates

`{"type":"catalog.watch","id":"catalog","collection_ids":["tg.gift.123"]}` watches up to eight collections; an empty list watches the directory. Initial subscription and reconnect send complete `catalog.versions` manifests matching unquoted ETags from `/catalog` and `/collections/{id}`. Public versions are opaque 22-character tokens: an unpadded Base64url encoding of a 128-bit digest, without a format-version prefix, for example `f3MgDfNxr-4kEnhwdAqItQ`. One presentation-layer converter namespaces the complete domain content revision and produces both HTTP ETags and WebSocket tokens. HTTP quotes the token (`"f3MgDfNxr-4kEnhwdAqItQ"`); compare the unquoted value for equality, without parsing, sorting or decoding it. A null collection value still means the collection is unavailable. Older prefixed ETags cause one normal 200 response with the new token, then ordinary 304 revalidation resumes. Prices and freshness do not invalidate catalog content. Changed active collections revalidate; inactive collections become stale until needed. Reconnect comparisons recover missed changes without discarding unchanged content. Retries use bounded exponential backoff with jitter.

## Upgrading clients

This contract uses `catalog.watch` and `catalog.versions`; the former catalog message names and operation-level `status` frames are removed. Targets are flat, without `gift`, `criteria` or `reason` wrappers. Navigation keys have no format-version marker or query fingerprint: unpadded Base64 with the ASCII-ordered, URL-unreserved alphabet `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ_abcdefghijklmnopqrstuvwxyz~`. Sort/direction and source are packed into one header byte; rank, identity and before/at/after edges preserve ordinary string ordering. No repeated-character grammar is needed. Treat the encoded token as opaque. Update backend and frontend together and restart existing watches; discard navigation keys from the previous format. Keys are positions interpreted within the supplied query, with sort/source validation rather than filter binding. Order results use half-open ranges and omit `next`; finite queries support an optional `snapshot` lease. Discard cached coverage from the former inclusive-range contract.


Method `valuation.query` shares `POST /valuations/query`: pass `target`, `currency_id`, an explicit nonempty `strategies` list and an explicit half-open `period` when selecting execution methods. Targets are `selection`, `gift`, direct `gift_attributes` or the batched `catalog` projection. An attribute target is `{kind:"gift_attributes",collection_id,traits:{model?,backdrop?,pattern?},number?}`: supplied trait IDs are checked against the collection and kind, with no listed gift ID required. The additive gift estimate needs no number; other strategies use the number when provided to narrow their observations. A URL/slug gift reference uses the configured Telegram user-session resolver, which can supply unlisted gift facts. Without that resolver or during temporary lookup failures, observed listings and executions supply the fallback. Numeric collection/number references use observed market data. All prices remain market-derived. A selection uses `{kind:"selection",collection_id,criteria:{models:[],backdrops:[],patterns:[]}}`; empty criteria select the whole collection. Discovery at `/valuations/strategies` advertises capabilities. The result contains one resolved target, currency, evaluation time, stale flag and independent typed strategy results. Successful results have `strategy`, `revision` and `data`; failures have `strategy`, `revision` and `error`. Static presentation comes from strategy discovery. Missing samples are structured price issues. Mean/median share one history scan, and the entire report uses one pinned snapshot. Cancellation and request deadlines use the ordinary request lifecycle; reconnect does not replay the request. The former gift-only method has been removed; gift queries use the same method with `target:{kind:"gift",gift:"Gift-123"}` and `strategies:["gift_floor"]`.


## Valuation subscriptions

`valuation.watch` accepts exactly the same `ValuationQuery` as HTTP and `valuation.query`. Send, for example:

```json
{"type":"valuation.watch","id":"prices","params":{"currency_id":"GRAM","strategies":["catalog_floor"],"target":{"kind":"catalog","collection_ids":["tg.gift.123"],"details":{"collection_id":"tg.gift.123"}}}}
```

Each `valuation.snapshot` has `{type,id,data}`; `data` is the same `ValuationResponse` as a finite query, including resolved target, currency, calculation time, stale state and independent typed strategy results with definition revisions. A snapshot atomically replaces the report. Any registered strategy can be selected, subject to its input contract; fixed execution periods observe late backfills as market history arrives. There is no automatic rolling period or durable replay.

For picker values, `catalog_floor` accepts a `catalog` target with one to eight distinct collection IDs. Optional `details` must select one of those collections and adds all known model/backdrop floors and an optional pair. Its result data is `{collections:[{collection_id,evaluated_at,floor,traits?}]}`. Traits always contain model, backdrop and symbol (`patterns`) maps plus an optional pair. Each floor is `{value:"exact-decimal",count}` or `{error:{code,message,...},count}`. `count` is distinct identifiable gifts deduplicated across venues. The same shape is used by `ask_floor` and each input floor in `gift_floor`; separate numeric evidence objects and listing counts are absent. An eligible unidentified criterion can supply a price with count zero. Currency and stale state are on the report, and each collection retains its own calculation time when other collections change.

Data changes and listing expiry are sampled at the one-minute refresh boundary. Availability-only changes update promptly, reuse calculation data and preserve calculation time. Unchanged refreshes send no duplicate snapshot. Identical queries share through up to 32 weak active-read entries and a completed-report LRU with at most eight distinct reads. The report LRU has no TTL: hits promote reports, capacity evicts least recently used cache owners, and freshness is still validated at the minute deadline before reuse. Active watches keep independent ownership after completed-result eviction. Up to 32 valuation watches can exist application-wide, in addition to connection limits. Cancel, replace or disconnect releases the lease. Reconnect with a fresh watch for an atomic baseline; retained client values stay stale until it arrives.

The `valuation.query` target may also be `{kind:"selection",collection_id,criteria:{models:[],backdrops:[],patterns:[],number:null}}`. `ask_floor` returns the lowest ask matching all conditions together, useful for bids. Alternatives within each group use OR; different groups combine with AND; omitted restrictions accept any value. This differs from the Any/All mode for browsing bid orders. Execution strategies accept the same target with an explicit period. At most 500 trait alternatives are allowed. `gift_floor` accepts direct `gift_attributes` or a resolved `gift` reference; broad `selection` criteria are not treated as an individual gift.

Discovery display fields contain `id`, `label`, `primary`, `format` and an optional RFC 6901 `path`. An omitted path selects the property matching the field ID; `path:""` selects the root metric used by flat `ask_floor` results. They select typed `{value}` or `{error}` metrics from result data; field order and precision belong to the strategy. Attribute previews use the independent catalog valuation, while the calculation popup retains all fields from the gift estimate's original report. A historical execution's price and a present-day estimate are distinct values.


Valuation reports use one tagged resolved target and one `{currency_id,evaluated_at,stale}` context. A resolved gift is `{kind:"gift",gift:{id,collection_id,number?,traits},slug?}`; its strategy data contains metrics, flat input floors with counts and a calculation basis. There is no gift-specific response format. WebSocket frames are encoded once before queue admission; the retained byte buffer is used for both byte accounting and fragmented writes.


Strategy discovery includes one input capability descriptor, for example `input:{targets:["selection","gift"],period:"unsupported"}`. Execution strategies advertise `period:"required"`. No separate top-level `targets`, `requires_period` or internal Rust input-contract enum is exposed. Discovery also advertises `purpose:"estimate"|"reference"`: gift previews and bot reports select estimates, while bids retain reference floors. Explicit API requests can select either purpose. Clients select strategies from these capabilities; the service resolves facts once and prepares typed strategy arguments internally. Explicit periods are rejected when none of the selected strategies consumes them. Criteria alternatives are sorted and deduplicated for shared reads; result strategy order follows the request.

Request failures contain only `{code,message}`. Strategy failures retain their strategy ID in the result, and individual metrics retain typed sample evidence. Internal actor identities, storage errors and portfolio-only contexts are not exposed. Unsupported target failures remain independent of other strategy results.

Valuation reports use the tracked response encoder for both REST and WS. The default success-response budget is 4 MiB (`ApiLimits.response_bytes`), independent of incoming JSON limits. Encoding uses bounded blocking workers, checks cancellation while writing and drains on shutdown. Oversized results return `capacity_exceeded` for that operation; they do not close a healthy socket.


Valuation queries and watches use the same typed result as REST: each outcome contains `strategy`, a static contract `revision`, and either `data` (metrics and calculation evidence) or `error`. Presentation definitions live in `GET /valuations/strategies`, independently of results. Match the result revision to discovery before rendering. On a mismatch, reload metadata once and reuse the report; persistent mismatches should wait for a later retry, rather than loop or issue another calculation. Fields specify metric IDs and exact decimal formatting with midpoint-to-even rounding; static `display.evidence` entries are labels and RFC 6901 pointers into typed data (for example `/count`); they are not numeric evidence wrappers. Execution strategies retain their richer sample details. Documentation has its own content revision.

Temporary per-strategy `unavailable`/`timed_out` results have an internal retry deadline of at most five seconds, bounded by earlier listing expiry. Watches reevaluate at that deadline even without a market event. Missing samples and permanent query-budget/target failures do not trigger this retry loop. A new watch ignores notifications predating its baseline but retains changes during initialization. Successful result shapes and cancellation commands are unchanged.

## Portfolios

`portfolio.watch` and finite `portfolio.refresh` accept `{"user_id":123,"currency_id":"GRAM"}`. HTTP `GET /portfolios/123?currency_id=GRAM` and `POST /portfolios/123/refresh` (JSON `{"currency_id":"GRAM"}`) return the same lightweight summary. No summary response includes gift rows. Refresh starts or coalesces a Telegram recheck; a new recheck within five minutes of the previous check’s completion returns `capacity_exceeded` with cooldown details.

Use `portfolio.query` or HTTP `POST /portfolios/query` for gift pages. Example parameters: `{"user_id":123,"currency_id":"GRAM","sort":"position_asc","offset":0,"limit":100,"filters":{"models":["model-id"]}}`. Filters support a collection, model/backdrop/pattern alternatives and an exact gift number; dimensions combine with AND and alternatives with OR. Sorting supports `position_asc/desc`, `number_asc/desc` and `value_asc/desc`; unknown values stay last. Selection totals/counts cover all matching gifts, not just the page. The result is `{version,offset,items,has_more,selection}`. Continue at `offset + items.length` with the same version and query; a nonzero offset requires a version. Changed data returns `restart_read`. Offset is bounded to 10,000; default/max limit is 100. Item versions remain unchanged when revaluation changes only timestamps/freshness, avoiding redundant page requests. The inventory must first be loaded through a watch or explicit refresh.

Start directly with `{"type":"portfolio.watch","id":"portfolio.1","params":{"user_id":123,"currency_id":"GRAM"}}`. Its first `portfolio.snapshot` includes cached totals, item version and progress without gift arrays. The first visit loads inventory; subsequent visits and reconnects retain it without Telegram rechecks. `portfolio.progress` updates only `refresh_id`, `progress`, `refresh_after` and `error`; intermediate progress is coalesced to at most two updates per second, while completion and failures publish immediately. Progress contains stage, checked/total and valued/collectibles counts, without inventory page counts; keep the last snapshot's inventory and valuation. Ignore progress with an older refresh ID. A new summary snapshot replaces inventory metadata and valuation totals together. Paged clients use the item version to replace visited rows atomically. Unknown totals remain absent; failed or partial refreshes preserve a prior complete report. Active portfolio estimates refresh at most once every five minutes after the previous valuation finishes, without rechecking Telegram. Inventory rechecks have a separate per-user five-minute cooldown measured from completion. New inventory does not bypass valuation cooldowns; cached results remain available until replacement.

Cancel using the ordinary operation ID. Cancellation releases the watch; an accepted explicit refresh can finish its bounded work for other callers. The connected bot must know the numeric peer and Telegram enforces gift visibility. Hosted gifts are not proof of ownership. No access hashes/session data are public. Portfolios are unavailable when Telegram is not configured. Limits and response byte budgets apply to snapshots too.

### Batch valuation

`{"type":"request","id":"batch.1","method":"valuation.batch","params":{"queries":[{"target":{"kind":"selection","collection_id":"tg.gift.123","criteria":{}},"currency_id":"GRAM","strategies":["ask_floor"]}]}}` is the finite counterpart of `POST /valuations/batch`. Send 1–100 normal valuation queries. The result is `{"type":"result","id":"batch.1","method":"valuation.batch","data":{"results":[{"data":{...}}]}}`. Each ordered entry has either `data` (the same report and strategy revisions as `valuation.query`) or `error` with a typed code and message. Input duplicates remain separate entries. Invalid batch sizes fail the operation; query/target failures remain per item. Calculation failures retain the usual per-strategy shape inside a successful report. All market reads use one admitted snapshot, with collection/currency statistics and requested pair reads shared. Slug lookups use the existing resolver with at most two in flight, before pinning market data. Cancellation and the existing request/response byte budgets apply. No batch subscription or unbounded background job is created.
