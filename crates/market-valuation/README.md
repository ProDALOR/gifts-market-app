# market-valuation

Gift valuation contracts, actors, calculations and lifecycle ownership. Requests, strategy IDs, marks, metrics, evidence and valuation errors live here. Shared gift identities, catalog lookups and lookup failures stay in `market-gifts`. Production reads use `market-replica::ReplicaReader` and the pure `market-gifts-hub` adapter. There is no production dependency on `market-actors`, HTTP or Telegram; data actors are used only in integration tests.

`ValuationHandle::start(&arbiter, reads)` starts one valuation actor on the application-selected Arbiter. `ValuationTask` is its ordinary supervised lifecycle task. Gift estimates, target reports and current market values share the same bounded floor cache and request budget. `reads` is the shared `market-replica::ReadExecutor`. The application owns `market-replica::ReadRuntime`, supplies its `ReadExecutor` to both data and valuation actors, and drains it after stopping the actor services. Handles cannot close the shared tracker. The generic `Service::start_on(&arbiter, id, factory, config)` accepts a factory receiving `Lifecycle`; callers capture a `ValuationSource` or other inputs in the factory. Actors share immutable replica snapshots; they do not copy full orderbooks or create a thread per strategy.

`market/mod.rs` owns `ValuationQuery`, `ValuationReport` and shared floor evidence; `types.rs` owns strategy IDs and error metadata; `portfolio/types.rs` owns opt-in portfolio contracts; `gift_floor/result.rs` defines the strategy-owned `GiftFloorValuation` and `GiftFloorEvidence`. Reusable metrics live in `types/metric.rs`. The optional `schema` feature enables OpenAPI metadata. `service.rs` owns the shared handle/watch lifecycle, `market/actor.rs` dispatches admitted work, `floors.rs` owns shared ask statistics, and `gift_floor/calculation.rs` implements `gift_floor`: collection, model, backdrop and matching model+backdrop floors; dimensionless model/backdrop multipliers; and the final mark. The final mark is `round2(min(matching floor, collection floor * unrounded multipliers))`. Only displayed multipliers and the final mark round to two decimals, using midpoint-to-even. Each metric carries a value or a typed issue. Multipliers require three distinct identifiable gifts for both the collection and selected trait. `ValuationMetric<T>` separates monetary `Amount` values from dimensionless `Multiplier` values while retaining the same decimal-string JSON encoding. Evidence groups `collection`, `model`, `backdrop` and `model_backdrop` each expose `listings` and `gifts`; `minimum_multiplier_gifts` states the threshold. Final errors retain their original code, sample evidence and typed failed `dependency`.

The shared valuation actor retains at most eight collection/currency statistics sets, with at most 20,000 aggregate/known-trait entries per set. Statistics are rebuilt on demand when relevant dependencies change, the earliest eligible ask expires or a five-minute safety age is reached. There is no periodic refresh task. Each preparation has a 30-second read deadline. Gift resolution and all statistics use one pinned view. Short cache locks cover only lookup and publication; validation and scans run outside the lock on read workers. The shared heavy-read lane serializes preparations. Traversal deduplication is bounded to 200,000 identity memberships per scan and releases the identity sets before caching aggregate prices/counts. Cross-listings share identity references during traversal and count once per floor. Broad criteria supply prices but cannot satisfy gift-count thresholds. The Arbiter remains responsive while work waits for capacity.

`portfolio.rs`, `portfolio/floors.rs` and `portfolio/calculation.rs` retain explicit quantity-based portfolio floors behind the opt-in `portfolio` Cargo feature, enabled by `market-portfolio`. Inventory and its Telegram transport remain available for future user portfolio integration. The gift API uses its own error-details projection so portfolio evidence is absent from OpenAPI even when workspace feature unification enables portfolio valuation. Each floor actor caches up to 16 normalized portfolios for 30 seconds. Relevant books and catalog references invalidate marks; unrelated updates preserve them. Name and Telegram lookups also track collection-directory changes that could introduce ambiguity. Restricted catalog rules read exact keys; unrestricted rules retain only the requested attribute while paging. Cached inputs with unchanged revisions need no worker slot. Freshness is rechecked after asynchronous validation; waiting does not renew a cached result.

`source/` owns valuation-specific catalog resolution, gift lookup, eligible asks and dependency checks. Generic bounded catalog paging belongs to `market-replica::catalog_read`, shared with data actors. `ValuationSource::prepare(callback)` returns the callback's result inside an execution result; fallible callbacks use `.await??`. Preparation pins the replica after admission. Snapshot reads, catalog loops and dependency checks cooperate with cancellation.

`ReadExecutor` executes both admitted API/data-actor queries and valuation work with one query budget and one tracker. Data actors retain a separate tracker only for live subscription producers. Heavy preparation is limited to one worker; small metadata checks use shared admission without occupying that lane. Dropping a caller cancels its worker token, which follows live and pinned readers into generic catalog helpers, but permits remain held until blocking work exits. Shutdown rejects new reads, cancels queued work and drains admitted work. Arbitrary blocking callbacks must cooperate with their cancellation token.

`runtime.rs` contains typed messages, bounded clients, `Prepared<T>`, `Mark<T>` and lifecycle tasks. Marks contain `{strategy, data, revision, evaluated_at, stale}`; the source revision stays internal and stale describes delayed updates in the pinned view. Admission defaults to 128 queued/running requests and a 30-second caller deadline; the valuation handle limits admission to 32. Dropping or timing out a caller cancels its request context. Dropping the task rejects new work and signals shutdown. Unexpected actor exit is reported by `task.run(stop)`; strategy panics remain failures even during supervisor cancellation; `task.shutdown()` waits for termination. `error.rs` maps replica failures into valuation error codes while retaining the original error as its source.

Run `CARGO_INCREMENTAL=0 cargo test --locked --offline -p market-valuation -p market-replica -p market-actors` for coverage of calculations, cache invalidation, pinned reads, bounded admission, cancellation and shutdown. Workspace dependency-boundary tests enforce the production crate direction separately from test fixtures.

Catalog traversals and order scans share a 2,560-page work budget, in addition to the 50,000-row/key catalog limits and statistics limits. Key chunks share a traversal budget; unmatched options consume it too. Exact catalog lookups read selected collection/model keys without loading unrelated directories. Name/Telegram lookups retain complete-directory ambiguity checks. Gift facts use the pure `market-gifts-hub::concrete_gift` projection, without constructing public order responses.

The strategy-owned `gift_floor/methodology.md` is the user-facing explanation of floors, formulas, sample requirements, rounding and limitations. It is embedded in the same binary as the calculation. The API serves it at `/valuations/strategies/gift_floor/documentation` with content-based ETag revalidation; the GUI loads its Markdown renderer and guide only when the user expands “How is this calculated?” in gift details. Update this file alongside any calculation change.

Each `Strategy` owns its ID, name, description and documentation as associated constants. The registry builds `StrategyMetadata` from them and the strategy's associated `Input` contract. The gift-strategy catalog exposes IDs, names, summaries and Markdown without transport URLs or mixing strategy result types. The API presents it at `GET /valuations/strategies` with `documentation_url` links; documentation routing looks up IDs in the same catalog. Portfolio-only library actors are not advertised as available API strategies.

Use `$...$` for inline LaTeX and `$$...$$` for display formulas in strategy Markdown. The GUI renders these with micromark's math extension and KaTeX, loaded only when a guide opens. Native MathML output keeps formulas accessible, respects the market's existing policy against inline styles and needs no extra math font downloads. Keep HTML and KaTeX trust disabled. The frontend pins one current KaTeX version via an npm override because the math extension's upstream dependency still targets an older release.

Registration is explicit in the gift-strategy catalog. The shared actor dispatches explicitly selected strategies; each result retains its own strategy ID independently of the service lifecycle. Discovery caches its serialized representation and per-guide ETags once per process. Every public descriptor includes `documentation_revision`, so a Markdown change also changes the discovery ETag.

The GUI shares a bounded, one-minute strategy catalog cache across order-detail sessions. Order details discover compatible period-free strategies, send one explicit selection, and retain metadata alongside the report. Choosing another returned strategy changes presentation without another read. The popup reuses that metadata; only the Markdown renderer and guide load on intent. Closing details cancels pending discovery or calculation. Failed discovery remains retryable and does not dispatch guessed strategy IDs. Guides are cached by URL and documentation revision within a byte limit. Discovery refreshes on the next use after expiry, without polling.

`ValuationDisplay` is a display projection, not a replacement for a strategy's typed result. `gift_floor/display.rs` selects fields directly from `GiftFloorValuation`: order, labels, primary emphasis, exact or fixed decimal precision, currency/suffix, summary and note. Each field has only an ID, label, primary flag and typed display value. The GUI keeps gift-strategy fields together in the calculation popup and uses the independent catalog valuation for attribute previews, including gift/listing evidence counts. Decimal formatting uses checked domain amounts and midpoint-to-even rounding; typed values retain their calculation precision. Shared helpers produce currency, number and unavailable display values, including readable error details. A strategy can construct these display values directly when it needs different labels or error formatting.

The API appends `display` to the typed response. The projection borrows the same result and needs no additional read or metadata request. The GUI consumes only the common result envelope and display protocol; it does not look up metric names, infer units from field IDs, choose a primary metric, or round decimal strings. Metadata remains responsible for the strategy name and documentation. Adding display fields therefore requires no field-list changes in the GUI.


`market/` separates valuation targets from typed estimators. `ValuationTarget` selects a collection, model, backdrop, model/backdrop pair, individual gift or accepted bid criteria; target validation reads direct catalog keys. `ValuationQuery` requires an explicit strategy list. `Strategy` has associated `Input: StrategyInput` and `Output` types. The algorithm receives its checked input plus `ValuationContext`; actor messages, target resolution, admission and transport are outside calculation implementations. `AskFloor` reuses collection aggregates, while `ExecutionMean` and `ExecutionMedian` reuse one bounded history traversal in their report context. `StrategyValuation` keeps outputs typed, and `StrategyOutcome` isolates per-strategy failures.

`ValuationHandle::query` prepares the report in one tracked worker and pinned snapshot. A coordinator evaluates estimators together so one report cannot mix revisions or duplicate execution scans. Calculations do not require an actor per target or strategy. History is bounded to 50,000 matching observations; explicit half-open periods cannot extend into the future. Mean weights execution records equally, independently of quantity. Collection/trait estimators require three records across three identifiable gifts; individual-gift targets require three records for that gift. Observed histories do not assert complete coverage or independent sellers. Strategy metadata advertises supported target kinds and whether a period is required. The composite output is a typed `StrategyValuation::GiftFloor` within the same report.


`FloorEvidence` belongs to the shared market contracts; it is not owned by `gift_floor`. The individual strategy consumes the same cached prices/counts as `AskFloor` and the batched `CatalogFloorValuation` strategy output. API, GUI and bot all use `ValuationHandle::query`; the former gift-only request/mark/response adapter has been removed.

`floor_projection.rs` implements the registered `CatalogFloor` strategy with `CatalogInput`. Its `CatalogSelection` accepts one to eight distinct collection IDs and optional details for one selected collection, including an optional pair. `CatalogFloorValuation` owns the compact typed collection/trait maps; report currency and stale state are shared context. It uses the same cached ask statistics as the individual and selection strategies. Known choices without asks retain typed `not_enough_data` issues; removed pairs have `missing_trait` without failing other values.

`ValuationHandle::query` and `watch` accept the same `ValuationQuery` and share `market/read.rs`. A `ValuationRead` retains internal catalog dependencies, observation dependencies, used statistics, relevant listing expiry and a one-minute freshness deadline. Strategies use `ValuationContext::orders` so execution backfills and narrow-ask expiry invalidate the correct source at the next refresh. `floors/cache.rs` owns one entry per collection/currency, containing a summary, optional traits and one refresh deadline. The table holds at most 512 entries; trait retention is bounded separately to eight projections. Trait LRU eviction leaves the summary and deadline intact. Summary requests do not promote trait recency, and summary sweeps cannot evict entries that still have loaded traits. `floors.rs` contains immutable statistics and preparation. Each cache read returns the shared statistics and a captured deadline, so report validation cannot move a cache timer and later cache hits cannot move an existing report's timer. Prepared traits and their summary refresh in one scan; trait-only metadata changes preserve an unchanged summary. Their covered metadata is not captured again by the report.

The report cache has two bounded responsibilities: up to 32 weak query entries share active reads, and a completed-result LRU owns at most eight distinct reads. Cache hits promote reports; least recently used cache ownership is evicted when capacity is reached. There is no report TTL, retention timestamp or periodic cleanup task. Dead weak entries are removed on access. Retention does not renew freshness: a report used after its minute deadline validates its dependencies and expiry before reusing unchanged results or recalculating changed data. Target, currency, strategy order and checked execution period define query identity. Superseded reports lose their cache owner immediately. Active watches retain their own reference and can still share through the weak index after completed-result eviction. Caches retain no replica snapshot.

Watches use the refresh timer and availability notifications rather than every order change. Availability-only changes reuse calculation data and preserve calculation time; large catalog outputs stay shared through an `Arc`. Unchanged refreshes advance the deadline without sending duplicate reports. Cancellation cannot lose a due deadline; dropping a watch or pending query releases its work through the existing lifecycle. The service allows at most 32 valuation watches, each with independent cancellation. HTTP and WebSocket use the same query and report contracts.

The GUI fetches summary-only `catalog_floor` batches for every collection at startup, then refreshes them every minute. Selected-collection trait maps and the current gift’s pair use a separate foreground `valuation.query` on the same connection; it supplies that collection’s summary too. At most two background batches and one selected-details request are active. Scroll and picker visibility do not trigger requests. Switching selections cancels obsolete details, while currency changes cancel all old reads. Minute refreshes do not overlap active work; reconnects refresh stale values. Every current catalog summary is retained, with at most eight trait sets within 8 MiB; recently selected traits can be reused for one minute. There are no per-option or per-card valuation requests. History shows current asks separately from the immutable execution price. A calculated gift estimate becomes outdated when its inputs change; its popup retains the original input basis and refreshing that estimate remains explicit. Public `valuation.watch` remains available to API consumers.

Criteria targets combine alternatives within each model/backdrop/symbol group with OR and groups with AND, plus gift-number bounds. Empty groups are unrestricted. The matching ask floor scans the complete selection rather than combining separate minima; a cheap model floor and a cheap backdrop floor may belong to different gifts. Criteria with at most 500 alternatives can use ask or explicit-period execution estimators. They cannot use the individual-gift composite strategy.


`ResolvedTarget` is a tagged enum: collection, model, backdrop, pair, criteria or a checked gift identity with optional normalized input slug. Missing or mixed payloads are rejected by Rust and described by the same OpenAPI union. `GiftFloorValuation` contains only metrics and evidence; currency/target/time/stale status live in `ValuationReport`. Strategy display borrows the report currency.

A collection's floor `evaluated_at` comes from its cached statistics and remains unchanged when another collection changes. Relevant book and model/backdrop/pattern catalog dependencies and listing expiry are checked at the next one-minute refresh. Changed statistics recalculate that timestamp; unchanged dependency checks preserve it. This is a calculation time, not a source cursor or listing creation time. Bid-estimate freshness compares against the selected collection only, retaining native sub-millisecond precision. Gift-estimate freshness additionally compares its typed floor inputs and evidence.


Typed strategy arguments live in `market/inputs.rs`:

- `CatalogInput` carries a checked bounded catalog selection for batched projections.
- `SelectionInput` shares one resolved target for collection, model, backdrop, combination, criteria or exact-gift selection.
- `ExecutionInput` combines that selection with an `ExecutionPeriod`. Both bounds are always present, `from < until`, and `until` cannot be in the future. Reads use inclusive `from` and exclusive `until`.
- `ResolvedGiftInput` carries the resolved gift identity, collection, number and model/backdrop/symbol facts. Optional facts stay optional. The current floor formula can still return partial metrics when model or backdrop evidence is missing; it does not require a symbol.

Each input implements `StrategyInput` and declares an `InputContract`: `catalog`, `selection`, `selection_with_execution_period` or `resolved_gift`. Supported target kinds and period requirements come from that contract. `/valuations/strategies` exposes `input` alongside the derived `targets` and `requires_period`, so clients can discover requirements without inspecting strategy IDs. Raw HTTP/WebSocket queries still use the same target/currency/strategy/period model. Query preparation validates IDs, duplicates and period once before admission, retaining static registrations and an optional checked `ExecutionPeriod`. Input contracts describe requirements without repeating request validation.

`strategy.rs` contains one typed registration table. A registration ties the strategy type, its associated input conversion and its typed result variant together. The actor resolves snapshot-dependent currency/catalog facts once in its admitted pinned worker, then passes the same checked period to each registered input adapter. A gift-only strategy can fail independently without discarding successful selection results. Execution does not repeat registration lookup or construct error context that the report would discard. `GiftFloor` implements the same `Strategy` trait in `gift_floor/strategy.rs`; the remaining algorithms live in `market/strategies.rs`. The former `Estimator` trait and target-bearing context helper are removed.

`market/context.rs` provides the pinned read view, currency, shared floor statistics and one bounded execution-cache slot. The slot is keyed by the complete execution input, including target and period; mean and median reuse the same successful scan or failure. Another selection or period cannot read cached observations for the previous input. Context holds no implicit target or optional execution period. Request/read limits, cancellation and supervised lifecycle remain shared.

Consumers select capabilities rather than registered algorithm IDs: `strategies_for(target_kind, has_period)` filters the Rust registry, and the GUI uses the equivalent derived discovery fields. This is request-building convenience, not domain validation; explicit HTTP/WebSocket selections still go through the same checked query preparation. The bot includes all compatible period-free gift strategies, labels independent results from registry metadata and renders each strategy's own summary/note. GUI target forms retain date-input checks for useful feedback; Rust owns authoritative historical-period validation. Detailed gift-floor freshness comparison remains a typed adapter for that strategy's evidence; unfamiliar results use conservative selected-collection change detection.

The catalog-floor projection includes independent symbol (pattern) ask floors and unique gift counts in selected collection details. All trait summaries share one bounded ask scan and cache; symbol floors do not alter the gift-floor estimate formula.
