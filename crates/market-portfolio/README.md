# market-portfolio

Shared visible-inventory workflow for bot and GUI, implemented as one supervised Actix actor. `market-app` starts it once outside HTTP workers when the Telegram bot is configured. It reuses the bot’s `InventoryClient`, the application invocation scheduler and `ValuationHandle`. Telegram RPC/session details remain in `market-telegram-client`; report presentation remains in API/bot/GUI adapters. The optional `schema` feature is enabled by the API; independent workflow consumers do not need OpenAPI dependencies.

`PortfolioService::start(provider, valuation, config, invocations)` returns `PortfolioHandle` and `PortfolioTask`. Run the task under application supervision or join it with `shutdown()`. Application shutdown drops in-flight page and valuation futures, cancels invocation tickets and joins the actor thread before draining invocations and shared market reads.

## Requests and progress

Subjects are validated numeric Telegram `UserId`s. A service instance belongs to one inventory provider/session scope; never share its cache across unrelated accounts. It serves only gifts that provider exposes for the requested peer. Numeric IDs are not authorization credentials or access hashes. The bot must already know the peer; its own private inventory is rejected. Imported user accounts used for gift-slug lookup are not used for portfolio enumeration.

- `query(PortfolioQuery)` reads current cached state without fetching Telegram inventory.
- `watch(PortfolioQuery)` returns an initial state and coalesced updates. The first uncached visit starts an initial inventory load; reopening/reconnecting does not recheck previously attempted inventory.
- `refresh(PortfolioQuery)` explicitly starts a recheck, or joins the current one. New rechecks have a per-user five-minute cooldown after the previous check finishes, independent of currency. Successful and failed checks both start the cooldown; concurrent callers join the running check. `refresh_after` is published at completion and is absent while checking. It returns current progress immediately.

`PortfolioState` keeps separate inventory/check timestamps and valuation timestamps. Stages are idle, queued, loading_inventory, valuing, ready and failed. Inventory progress includes scanned gifts and an optional Telegram-reported total; page counts stay internal. Valuation progress counts collectibles processed. Unknown totals remain indeterminate. Refresh IDs reject late work from replaced scans; valuation progress and completions are additionally bound to inventory generations and valuation attempts. An explicit recheck cancels the old valuation before fetching inventory pages.

A previous report and its inventory summary remain visible together until the new valuation succeeds. Inventory and estimates replace atomically per currency. Failed or partial rechecks never replace a prior complete inventory. On a first partial load, the partial result is explicitly labeled. Hosted/unverified gifts keep their relation; visibility does not assert ownership. Minted gifts returned in the profile inventory without owner/host peer IDs are retained as `unverified`, including those with a wallet address. Explicit links to another profile, burned/refunded gifts and malformed gifts remain excluded. Bot reports and GUI cards/details label unverified ownership; these gifts still count toward estimates when priced. No wallet address lookup or blockchain inventory scan is performed. Regular and unsupported gifts are counted separately. The Telegram API does not provide a transactional snapshot across inventory pages, so gifts changing during a scan can affect its completeness.

Disconnecting an observer drops its watch lease and stops periodic market valuation work once no observers remain. An accepted user-triggered inventory recheck completes its bounded job for the shared cache even when its initiator leaves. Shutdown cancels it. The service never performs periodic Telegram rechecks.

## Scheduling, caching and valuation

Providers construct one unsubmitted typed invocation per page. The actor owns pagination and submits it with interactive priority; `market-invocations` owns shared rate limits, flood waits, retries and transport cancellation. Two inventories can be in flight; pages for one user stay sequential. Queue and request deadlines include waiting for admission.

Defaults bound the workflow to 128 callers/watch leases, 64 cached users, eight currency views per user, 50,000 retained inventory gifts globally, 100 gifts per page, 10,000 scanned gifts and 100 pages per inventory. Inactive entries are evicted by user LRU after their check and valuation cooldowns expire; active watches/jobs and cooling entries are protected. Currency views follow the same rule, so eviction cannot reset the limit. If all slots are protected, new subjects return capacity errors rather than bypassing cooldowns. Full API snapshots also respect the existing response byte limit (4 MiB by default); oversized responses return a typed capacity error. There is no disk inventory cache or unbounded background queue.

Every scanned item must be accounted for. IDs deduplicate across pages. Malformed accounting is an error; repeated/missing cursors, scan/page limits and later page failures produce partial outcomes. Permission/authorization failures remain failures, including on later pages. The inventory deadline defaults to 60 seconds. Valuation has no total-duration cutoff: its 60-second inactivity deadline resets only when the processed gift count increases. Repeated counts and closed progress channels do not keep stalled work alive. A stall cancels that attempt while retaining the previous report; active views retry after the normal refresh interval.

`ValuationHandle::inventory` projects estimates through the shared typed batch engine used by REST/WS batch valuation, using the current `GiftFloor` strategy with one pinned, cancellable shared read job. The portfolio keeps its independent inactivity timeout and 10,000-gift bound; the public finite batch accepts at most 100 queries. Telegram catalog aliases are resolved in a batch, with one choice read per collection/trait kind rather than a lookup per gift. It shares the same collection statistics and read budget as individual valuations. Inventories share one immutable gift vector across currency views and valuation jobs. Gifts are grouped by collection and returned in their original order. Floor preparation traverses shared order references without cloning full paginated order responses; cancellation and scan/membership budgets remain enforced. Each collection is prepared once per pass, its context reuses pinned statistics even after global cache eviction, and repeated model/backdrop appearances reuse their pair-floor read; no Cartesian product is prepared. Unrestricted alias directories are read once per kind, shared across collections, and retain only requested aliases. Internal progress advances during valuation and at collection boundaries. Public intermediate updates are sampled at most twice per second; stages, completion and failures publish immediately. Every advancing internal count still resets the inactivity timeout, even when it does not produce a public frame. Logs separate admission, catalog resolution and total valuation time. Sums use checked decimal arithmetic. Unknown traits and missing prices retain gifts as unpriced and exclude them from totals; an entirely unpriced inventory has `total: null`.

Active currency views revalue cached inventories at most once every five minutes after the previous run finishes. Failed, stalled and superseded runs also start this cooldown. A new inventory does not reset the valuation deadline: the previous report stays available until the next eligible pass replaces inventory and values together. A failed inventory check keeps the previous report without revaluing it; an explicit successful recheck resumes valuation. Currency/filter changes reuse inventory; inactive views do not poll market data. The current gift-floor formula ignores number and symbol premiums, so they remain filter/display attributes rather than additions to the total. Estimates are based on observed market asks, exclude fees and are not guaranteed sale prices.

## Public adapters

REST: `GET /portfolios/{user_id}?currency_id=GRAM` and `POST /portfolios/{user_id}/refresh` with `{"currency_id":"GRAM"}` return a lightweight `PortfolioResponse`: progress, inventory metadata and full valuation totals, without gift rows. `POST /portfolios/query` reads a page with the same `PortfolioReadQuery` used by WebSocket `portfolio.query`. Responses use `Cache-Control: no-store`.

WebSocket `portfolio.watch` and finite `portfolio.refresh` take `{"user_id":123,"currency_id":"GRAM"}` and send only summary/progress data. Finite `portfolio.query` takes the subject plus `filters`, `sort`, `offset` (default zero), `limit` (default/max 100) and `version` (optional only on the first page). The page contains `items`, `offset`, `has_more`, `version` and a `selection` summary over the entire filtered inventory. Reuse its version for continuation; changed items or profile order return `restart_read`, never mixed pages. `PortfolioReadCache` retains at most 32 compact filtered/sorted position indexes, with no report/inventory references. Identical reads share one build; scans and sorting run outside the global cache lock. Page responses share immutable selection metadata internally. Projection and encoding share bounded, cancellable, tracked API workers. Bot reports continue using the full internal inventory. API-only deployments return unavailable without Telegram configuration.

GUI `/portfolio/<user_id>` shares market cards, collection/rarity pickers, gift details, valuation breakdown and virtualized grids. Visible cards and opened details reuse the same catalog controller and artwork as market asks. Metadata loads on demand for up to 32 nearby/selected collections, with two concurrent HTTP reads and catalog watches in groups of eight; scrolling never preloads the entire portfolio catalog. Picker options stay scoped to their selected collection. Details follow the current report by gift ID and close if a refresh removes that gift. Position sorting follows Telegram inventory order, which is preserved across page merging and duplicate removal. Collection/trait pickers and the selected-trait preview reuse market controls; All gifts clears the collection/trait selection. Gift number and position/number/estimate sorting remain available; estimate range controls are removed. Filters and sorting run on the full server inventory; the compact estimate panel shows the selected total and count with the full portfolio total as context. A shared shell keeps filters, currency and scroll position when navigating between Market and Portfolio, releases inactive watches and handles browser/Telegram Back. Mini App self-selection uses authenticated identity. Reopening and changing currency use cached reports; only Recheck refreshes previously attempted inventory. Hidden tabs release watches. Resume/reconnect keeps cached rows visible but waits for a fresh watch summary before reading pages. Pending scroll coverage survives cancellation and version changes; replacement rows commit atomically. Failed pages retry explicitly or after reconnect, rather than on every progress update. Equivalent trait selections reuse the same page cache regardless of selection order. The bot supports `/portfolio [user_id] [GRAM|XTR]`, throttled progress edits, cached page navigation, explicit recheck and GUI links. Normal private-message progress edits one reply instead of creating a message per page.

Tests: `cargo test --locked -p market-portfolio -p market-valuation -p market-api -p market-telegram-bot -p market-telegram`. No live Telegram calls are required.

Frontend regression checks: `npm --prefix web run test:portfolio` and `npm --prefix web run test:navigation` use isolated synthetic services on desktop and mobile, without Telegram calls.
