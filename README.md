# Gifts Market App

A public React market browser with a Rust REST/WebSocket API and a persistent local read replica. Market Hub receives and validates authoritative facts. Each app instance synchronizes those facts once, then serves catalog, order and execution queries locally. Public requests never query the hub.

```text
Adapters → Market Hub ── snapshot + Watch ──→ App replica → REST / WebSocket → React
                          └───────────────→ Another app replica → more visitors
```

Each app process shares one replica across its HTTP workers. Current catalog, feeds and active-order indexes live in RAM. Execution payloads remain in local redb, with chronological, book and typed attribute indexes. Current entities are also persisted so a saved checkpoint always describes fully restorable state. There is no sibling Rust dependency: the copied `market-hub.proto` is the service boundary and the replica stores its generated messages directly.

Active orders belong to venue/collection/currency/side partitions, alongside their price, time and gift-number indexes. Ranked indexes share each partition's immutable order records. A global ordered location directory routes venue/order IDs to their current partition and preserves identity cursor ordering; catalog and feed records remain in a separate metadata map. Readers and revision tracking access both through `State` lookup and iteration methods. Same-partition replacements preserve location entries and remove only changed ranks. Snapshot views share unchanged partitions through copy-on-write. See the [partition-owned orders benchmark](docs/partition-owned-orders-benchmark.md) for measured read, update, allocation and memory tradeoffs. The database and cursor formats are unchanged.

## Run

Issue a service token on the hub with `market-hub token --id market-app`, then configure this application:

```sh
export MARKET_HUB_TOKEN='<issued service token>'
npm --prefix web ci
cargo build --locked -p market-media --bin market-media-render
npm --prefix web run build
cargo run --locked --bin market-app -- --hub-url http://127.0.0.1:50051 --data-dir data
```

Open `http://127.0.0.1:8080`. The interface provides collection search, separate quote currencies, unified or single-venue asks and bids, exact price/time/gift-number ordering, catalog trait filters, history and order details. Live scrolling replaces the active ordered-range watch in either direction while retaining visited rows. The grid mounts viewport rows plus overscan, keeps card heights stable, and preserves the visible order as range snapshots and atomic change batches arrive. Active range updates are coherent; cached regions refresh when revisited. Filters stay in the URL; asks, bids and history update live, and reconnect resumes around the visible order. Executions are confirmed facts from adapters; disappearing listings do not imply sales.

The service token stays on the server. Visitors need no hub credentials. Native configuration uses `MARKET_HUB_URL`, `MARKET_HUB_TOKEN`, `MARKET_HTTP_ADDR` and `MARKET_DATA_DIR`, or their CLI options. Every app instance needs its own data directory. It is bound to the source hub URL and service identity; use a new directory when connecting to a different source.

SVG generation builds with Cargo alone. For release deployment, build both binaries with `cargo build --release --locked -p market-app -p market-media --bin market-app --bin market-media-render --all-features` and deploy them together. Docker includes both automatically. A missing helper leaves thumbnails and TGS playback available.

For frontend development, start the Rust application and run `npm --prefix web run dev`. Vite proxies API and WebSocket traffic to port 8080. Rust serves `web/dist` normally; set `--web-dir` or `MARKET_WEB_DIR` for another location. Use `--no-web` or `MARKET_NO_WEB=true` to serve only the API, without frontend files or routes. Embedded `ApiConfig` defaults to `web_dir: None`; pass `Some(path)` to enable frontend hosting.

Deployment limits use `MARKET_HTTP_WORKERS` / `--http-workers` (default 2), `MARKET_MAX_CONCURRENT_QUERIES` / `--max-concurrent-queries` (32), and `MARKET_MAX_LIVE_QUERIES` / `--max-live-queries` (128). Live-query capacity counts producer tasks. Catalog watches and identical resolved order coverage share one live slot and retain independent leases. Order initialization has a separate bounded pool with the same live-query limit; joining an exact, current range skips initialization reads. These limits are separate from WebSocket connection limits. CLI flags take precedence over environment values. Native runs do not automatically load `.env`; export its settings before starting the process. Compose loads `.env` automatically.

Configuration migration: `MARKET_CORE_URL` / `--core` became `MARKET_HUB_URL` / `--hub-url`; `MARKET_NODE_TOKEN` / `--node-token` became `MARKET_HUB_TOKEN` / `--hub-token`; `--workers` became `--http-workers`; `--max-streams` became `--max-live-queries`. Remove `MARKET_TELEGRAM_BOT_ID` and `MARKET_TELEGRAM_BOT_USERNAME` from worker deployments. For Mini App-only deployments, replace them with `MARKET_MINIAPP_BOT_ID` and `MARKET_MINIAPP_BOT_USERNAME`. Old names are no longer read. Keep the same hub URL, issued token and data directory when migrating to preserve the replica binding.

## Synchronization and recovery

A new replica opens a coordinated hub snapshot session, pinning current entities and execution history at one Watch checkpoint. Two independent gRPC connections consume its current/history parts; a third carries Watch and control requests. The app starts Watch after the first page and spools changes to disk while consuming both parts. Up to eight pages, 4,000 entities and 4 MiB form one staging batch; one overflow page may wait. Ready Watch deliveries coalesce into at most 64 records per journal transaction, under 2 MiB of encoded payload, preserving replay positions. One serial storage executor builds the unpublished replica, replays the journal and atomically publishes only after both parts finish. Missing final markers, inconsistent checkpoints and failed parts abandon the entire build. Existing data remains available during recovery. Older hubs use paged `Read(SNAPSHOT)` only when coordinated snapshot setup returns `UNIMPLEMENTED`. The intermediate full-stream `Snapshot` RPC has been removed. See [bootstrap measurements and recovery](docs/bootstrap-performance.md).

Bootstrap overlaps bounded snapshot batches with staging, mutates unpublished indexes directly with failure recovery, replays journal deliveries in bounded groups, and logs index, storage, queue and publication timings. See [bootstrap performance and recovery](docs/replica-bootstrap.md) for bottlenecks, measurements and troubleshooting.

Normal operation needs one authenticated Watch stream through a reusable gRPC channel. Ready deliveries publish a new RAM/history view without waiting for disk. A dedicated `replica-persistence` thread writes them in order and coalesces only already-ready jobs, without a collection timer. The queue is bounded to 256 jobs and 16 MiB of estimated payload; saturation returns explicit backpressure. New executions merge into a small immutable indexed tail immediately, so active removal and history visibility remain atomic before persistence. Completion refreshes the durable base without invalidating logical revisions or pinned readers.

A successful live publication is not a durable checkpoint. Reconnect and graceful shutdown drain accepted writes; restart resumes only the cursor committed atomically with its covered facts. Hard crashes may lose unflushed live updates; Watch replay or a replacement snapshot repairs them. Repeated acknowledgements at the published checkpoint need no write, and identical observations/execution retries avoid data invalidation. Execution timestamps determine history order; opaque Watch cursors determine replication progress, retaining late backfills.

Internal entity kinds, order modes, sort order and index tags use validated enums. Entity and execution keys have named fields; numeric codes and tuple layouts are converted at the protocol, database and continuation boundaries. Existing databases and valid pagination tokens keep their original format.

After local state is restored at startup, saved state is available while market updates are delayed. The app resumes Watch from its durable checkpoint. If the cursor expired or the hub restarted, it builds a replacement database while continuing to serve the previous copy. Completion swaps catalog, active orders and history together; facts absent from the replacement snapshot disappear too. An interrupted build is discarded on startup.

Clean startup validates the existing schema and service identity in a read transaction, reuses persisted execution ranks, and restores current records through an insert-only path. Order identities are shared across the location directory, ranked indexes and trait memberships. Only an empty database is initialized. Missing service identity or required data tables are rejected without adopting the saved checkpoint; missing execution ranks are rebuilt transactionally, and a missing staging journal can be recreated. Existing snapshots, checkpoints and cursors need no migration or data reset. See [startup measurements](docs/startup-benchmark.md).

Startup logs begin before local database recovery. Named phases report their duration and emit `startup still in progress` every five seconds while pending. Database open, optional execution-rank rebuilding, restored current-state rows/order indexes, revision indexes, media cache and HTTP initialization are visible separately. Large restores report row progress without additional scans; an interrupted snapshot build is logged before removal. `market app services started` means process initialization is finished, while `/readyz` and `market.status` continue to report actual data availability. The default Docker `RUST_LOG=info` shows these messages; a higher log threshold suppresses them. These diagnostic changes do not change storage formats or require Docker cache clearing.

SIGINT/SIGTERM handling starts before startup work is polled. Replica restore, execution-rank repair and media scanning stop cooperatively between operations; the current redb operation or filesystem call finishes safely first. Startup failure and cancellation drain started services, reads and media work through the normal shutdown path. Accepted live writes still drain to a durable checkpoint. Abandoning a startup future requests cancellation and keeps database cleanup on storage workers; its directory lock is released when that cleanup finishes.

Market reads remain available during update delays. The connection-level `market.status` message reports `available`, `delayed` or `unavailable`, without storage or synchronization metadata. The GUI shows **Updates delayed** when fresh updates are interrupted. Valuations retain their calculation time and a `stale` flag; raw hub cursors and sync state are absent from public results and errors. `/readyz` still succeeds when saved market data can be served.

The local database is a rebuildable cache, not the authoritative archive. Stop this app and remove `replica.redb` and `building.redb` from its data directory to rebuild it. Preserve `session.key`, which signs user sessions independently of market replication. Never share a redb directory between running app instances. Disk usage includes execution history and, during a rebuild, the replacement database and its change journal.

## Docker

Copy `.env.example` to `.env` and set a reachable `MARKET_HUB_URL` and an issued `MARKET_HUB_TOKEN`. The app joins an existing Docker network named `market`; set `MARKET_NETWORK` in `.env` to use another network. The hub container must join the same network to be reachable by service name. If the hub is remote and you have no existing network, create it once with `docker network create market`. Start with:

```sh
docker compose config --quiet
docker compose up --build --detach
docker compose logs --follow --tail=100 market-app
```

Place your exported `accounts.json` beside `compose.yaml` before starting Compose; it is mounted read-only at `/app/accounts.json` by default and must be readable by UID 10001. See [user-session setup](#optional-user-session-for-slug-lookup).

Compose reads runtime configuration from `.env`; unset options use application defaults. Container data, bot, media and frontend paths are fixed to `/data`, `/bot-data`, `/data/media` and `/app/web/dist`, so native paths in `.env` do not override the mounted directories. Custom container paths require a Compose override with matching writable mounts. The listener is fixed to `0.0.0.0:8080`; `MARKET_APP_PORT` controls the published host port. After editing runtime settings, run `docker compose up --detach` to recreate the service with the updated environment.

Compose starts only this application, connects to the configured hub URL, publishes `0.0.0.0:8080` and persists its replica in `market-app-data:/data`. `MARKET_APP_PORT` changes the published port. Separate deployments use separate volumes. Multiple instances can sit behind a load balancer; retained snapshot pagination requires affinity to the instance holding the view. Query positions can move between instances synchronized to the same market.

For a hub running on a shared Docker network, configure `.env` with its service name and network:

```dotenv
MARKET_HUB_URL=http://market-hub:50051
MARKET_NETWORK=market
```

`MARKET_NETWORK` is used directly by `compose.yaml`; all deployments use the same `docker compose` commands. The network is external: Compose requires it to exist and leaves its lifecycle to the hub or administrator. When migrating from the former network override, use `docker compose up --detach` to recreate the app on the selected network. Existing data volumes are retained.

One Docker image includes the frontend, REST/WebSocket API, Telegram bot and Mini App support. A direct build uses `docker build -t market-app .`. The bot starts automatically when all three Telegram credentials are configured; serving the website and API requires none.

The image binds `0.0.0.0:8080`, stores the replica in `/data` and bot state in `/bot-data`, and runs as UID/GID 10001. Preserve both directories when running outside Compose. The image uses standard `SIGTERM` shutdown; Compose allows 15 seconds to drain workers.

The container becomes healthy when market data can be served, including saved data during an update outage. If it stays unhealthy, check `docker compose logs --tail=100 market-app` and `docker compose exec market-app curl --fail --silent --show-error http://127.0.0.1:8080/readyz`. Detailed synchronization and upstream retry diagnostics remain in application logs. `/healthz` checks the process; `/readyz` checks data availability. Both remain operational probes and are omitted from the consumer OpenAPI reference.

The Dockerfile has three stages: Rust compilation, frontend compilation and the final runtime image. The preview helper is built alongside the application; it requires no separate toolchain. A single `.dockerignore` excludes credentials, local state and generated assets from the build context. The frontend build generates public OpenAPI and TypeScript types before building React. Generated clients, dependencies and built assets are ignored. The Node build exports its schema using the compiled Rust binary.

Market and portfolio share the same gift cards, artwork, valuation details and virtualized grids. The shared application shell provides desktop sidebar tabs and mobile/Mini App bottom navigation. Thumbnails and animations are downloaded, and SVG previews are generated, dynamically at runtime and are never committed or bundled into Docker images. `MARKET_MEDIA_DIR` / `--media-dir` selects the persistent disk cache; the default is `<MARKET_DATA_DIR>/media` (`/data/media` in Compose, on the replica volume). The bot’s shared grammers client downloads cache misses directly from Telegram. An instance without bot credentials serves existing cached files and can generate previews from cached TGS; missing original media returns 503. Use separate cache directories per writable node; never share the replica database directory between running instances. Custom container cache paths must be on a writable mounted volume. An uncached media asset also returns 503 while the Telegram connection is unavailable. Deleting the media directory safely rebuilds the cache on subsequent downloads.

An enabled bot worker shares its authenticated grammers client with the media downloader; no second Telegram login or update consumer is created. All media downloads and SVG generation are demand-driven; startup performs no warmup or prefetch. Cache entries and pending requests are keyed by document ID and media kind, so each variant is downloaded once and failures do not affect the other variant. The pending budget is 64 assets, with at most four concurrent downloads paced 75 ms apart. Download requests use a bounded FIFO queue; abandoned queued requests are skipped. Downloads time out after 15 seconds and callers after 30 seconds. Original compressed files are limited to 256 KiB; generated SVGs are capped at 1 MiB. Negative caching and Telegram flood-wait cooldowns prevent retry storms. A 16 MiB memory LRU with a five-minute TTL avoids repeated disk reads, hashing and TGS validation, including for conditional HTTP requests. Response bodies share the cached byte buffer. The disk cache evicts its least recently used files above 512 MiB; startup and background maintenance every minute remove recognized temporary files older than one hour and obsolete converter-version previews and retired numeric-ID `*.placeholder.svg` files. Unrelated files are preserved. Cold reads validate and decompress outside the directory index lock; atomic writes keep partial files out of responses. Directory scans run in the background, and shutdown drains tracked disk work and stops and reaps native child processes. Transport reconnects replace the media fetch connection together with the command connection; disk hits continue to work during outages.

The Telegram adapter coalesces document resolution across thumbnail and TGS misses, caches up to 128 private references for five minutes, and refreshes an expired file reference once. It downloads either a static thumbnail or the original `application/x-tgsticker` document. Model and pattern document IDs share the same cache without exposing Telegram download credentials. The cache stores `<document-id>.thumb` and `<document-id>.tgs` independently. First-frame SVGs use `<document-id>.preview-5-<source-sha256>.svg`, so changed TGS bytes or converter versions cannot reuse an old derivative. Preview requests coalesce after resolving the original TGS and share memory/disk quotas. Two rendering jobs run at most; each has a ten-second timeout. The converter runs out of process without Rust FFI, receives only validated local TGS/JSON, and has no Telegram credentials or download role. Last-consumer cancellation kills and reaps the child before releasing its conversion slot. TGS is validated as gzip-compressed vector animation JSON before storage: expanded JSON is capped at 2 MiB, with bounded dimensions/duration and no external assets or fonts. Expression metadata is discarded only from properties with baked values/keyframes, before caching and delivery; expression-only properties remain rejected. Ordinary TGS files retain their original bytes. The API serves validated compressed TGS bytes without `Content-Encoding: gzip`; the lazy frontend decoder expands them for the player. Both variants support ETags/304 and a one-day browser cache. Browser previews share pending downloads and one media failure policy. Missing or invalid assets are cached for 60 seconds; transient failures cool down for two seconds or the full server Retry-After. Cancellation and queue pressure are not cached as missing media. Failures use the same bounded resource retention as successes. Visible image recovery waits for retry deadlines without holding download slots, validates native decoding before remounting and stops when hidden or unmounted; a later visible use can retry expired failures. Animation data has a 16 MiB weighted cache; decoded pattern images and tinted frames each have a 2 MiB RGBA cache. Concurrent pattern requests share decoding and tinting. Each renderer gets its own copy of animation data. Visibility, motion and resize observation are pooled across previews. Offscreen backdrops release their canvas buffers and local tinted-frame references; selected backdrop color bands use CSS gradients. The transport-independent `market-media` crate owns disk caching and request coordination; `market-telegram-client` owns authenticated downloads, `market-api` owns catalog lookup and HTTP delivery, and `market-app` wires them together. API-only builds retain no Telegram dependencies.

The dispatcher runs up to eight interactions concurrently, with one active command per chat or inline-message edit target and at most 64 received, uncheckpointed deliveries. Commands in the same chat retain their order. Checkpoints advance only through the completed prefix of received updates, so a later fast command cannot skip an earlier unfinished command after restart. Backpressure stops receiving when that window is full. In-progress receive futures survive other command completions. Command handlers have a 40-second deadline and at most three attempts; failures and panics produce a command-level response. Permanent reply rejections finish only that delivery. Transient sends retry with a 15-second timeout per attempt and honor full flood waits; cancellation leaves unfinished deliveries uncheckpointed. Private replies retain stable random IDs; inline and guest responses retain their query identities. Plain fallbacks are bounded without splitting characters, while oversized rich markup is dropped intact.

The GUI shows padded Exact / Compatible buttons with matching semantics in tooltips. Exact is the GUI default and maps to `bid_match: "all"`; Compatible maps to `"any"`. | Metric | Meaning |
| --- | --- |

Floors, premiums and the additive estimate retain exact quote precision. Only explanatory multipliers and the final mark round to two decimals, using midpoint-to-even. Ratios are not inputs to the estimate. Clients compare tokens only for equality. Older prefixed validators revalidate once automatically, without clearing caches. A React-independent catalog controller owns resource revisions, requests and retries. ## Queries, ranges and WebSockets

The GUI and external clients use one unversioned query API: `POST /orders/query` and WebSocket method `orders.query` share `GiftOrderQuery` and `OrderReadResponse`. All order operations use half-open `range:{start,end}` bounds, with null for an open head or tail. Queries default to at most 100 rows; the returned range end is the next page's inclusive start. Keys are reusable across filters with the same sort and source. Watches use the same flat query model: `orders.watch` reads up to `limit` rows, establishes their actual covered range atomically, and returns a snapshot with `range`. It then reconciles that fixed coverage with consecutive `orders.changed` batches. Later updates return complete coverage up to 100 rows or a capacity error. Snapshots always replace the subscribed state; gaps and reconnects start a fresh watch. No order revision, duplicate sort key, `next`, page token or per-watch sync frame is exposed. Finite WebSocket order results flatten `data`, `range` and optional `snapshot` at the envelope level, matching REST payloads.

Clients apply order changes atomically by removing deleted and replaced identities before merging the sorted upserts. The GUI builds each batch before committing its snapshot and lookup index, without depending on the internal structure of opaque ordering keys. The identity index keeps sparse updates efficient. Retired paging, sync, revision and reset fields are rejected by the frame validator.

Live `orders.snapshot` frames contain `type`, `id`, `sequence`, `data` and `range`; finite queries also support an optional frozen-view ID. Changes contain only sequence, upserts and removals. There is no operation-level connecting frame. `catalog.watch` returns `catalog.versions` manifests whose content versions match HTTP ETags, allowing clients to refresh changed catalogs without downloading unchanged entries on reconnect.

Ordering keys omit format-version markers and query fingerprints, retain sort/source validation and preserve exact lexicographic order with a compact encoding: packed decimal digits for prices, integer ranks for timestamps and gift numbers, and no rank payload for active identity ordering. A single byte packs sort/direction and source; history identity/time keys carry execution time once. REST and WebSocket ranges can reuse positions across filters; the supplied query determines all matching rows. Price positions are interpreted in that query's currency without conversion or validation of the original currency. This changes public navigation-key encoding without changing durable index formats. Deploy backend and frontend together, restart existing watches and discard old navigation keys.

Latest reads retain no view. Explicit snapshot reads preserve stable traversal during updates; `DELETE /orders/query` releases the lease. The GUI starts with one WebSocket watch that seeds 80 rows, queries additional pages as needed, retains visited listings, watches viewport coverage with headroom below the 100-row cap, and preserves scroll anchors. Asks, bids and history share one query type, including execution-period filters. The controller tracks covered intervals separately from cached rows: a limited reconnect baseline retains older rows and marks the interval before the retained tail unread. Bounded queries fill gaps without rereading the whole cache or declaring pagination complete too early. Viewport watches stay within contiguous covered intervals.

Pagination waits for a live baseline after reconnecting; an outstanding page is canceled and its intent resumes against current unread coverage. Empty filtered pages continue scanning, while transient failures respect backoff. Typed watch state and market availability jointly determine status, so an available market cannot mark an errored or reconnecting subscription Live. Subscription retries use socket-owned backoff and the latest visible anchor. Delayed pages cannot overwrite newer watched rows; collection changes close the old feed before layout callbacks run. Explicit frozen reads rebuild through the visited tail, including gaps, before publishing a replacement snapshot. Read, scan, memory and outgoing-byte budgets remain enforced. See [the WebSocket protocol](crates/market-api/src/websocket/protocol.md) for complete navigation, snapshot, status and cancellation semantics.

Ranked ask queries use per-partition enum memberships for selective model, backdrop and symbol filters. Reads choose the smallest matching trait group, reuse the authoritative shared order records and apply the remaining filters before returning results. This avoids exhausting the 10,000-candidate scan budget on unrelated listings when refreshing a sparse live range. Memberships follow order updates and removals, survive pinned reads through copy-on-write and rebuild from stored orders at startup. Candidate preparation remains bounded; bid constraints retain their separate Any/All matching semantics. No storage or protocol migration is needed.

API errors use `{error:{code,message}}`, including JSON, query/path extraction and framework errors. Invalid parameters return 400, oversized JSON returns 413, unsupported content types return 415, unknown routes return 404 and unsupported methods return 405. JSON query bodies are limited to 64 KiB by default. The same extractor policy is installed by the public route configurator and the full server.

WebSockets reserve operation IDs during asynchronous setup, so pings, cancellation and shutdown remain responsive. `cancel` stops a request or subscription. Validation failures with a valid unused ID return a correlated terminal `error`. Reusing an active ID or sending a command without a valid ID produces nonterminal `command_error`, preserving active work; only the latter has an empty ID. Connection failures use WebSocket close frames. Socket writes are polled concurrently with commands and operation jobs, so backpressure cannot block cancellation. An internal generation filters queued frames and late completions, while clients use fresh wire IDs to ignore frames already sent for canceled operations. The browser uses the socket's native connection state, bounds handshakes to ten seconds and detaches callbacks and timers on close. Reconnect restores subscriptions without replaying one-shot requests; unchanged query updates preserve their local snapshot and sequence. An oversized page produces a terminal subscription error and releases the ID. Slow consumers close with code 1013 so clients can reconnect and resubscribe. Order snapshots and change batches encode on four tracked blocking workers and enforce the output limit while writing. Shutdown drains encoding jobs after closing connections.

`ApiLimits` and `WebSocketLimits` centralize service bounds. Defaults are 256 WebSocket connections across HTTP workers, 16 pending/active subscriptions and eight requests per socket, 64 KiB input messages, 4 MiB encoded order responses, and an outgoing application queue bounded to eight messages and 8 MiB. The HTTP request-head receive timeout and extraction/handler deadline are both 10 seconds; exceeding the handler deadline returns a structured `503 timed_out` error. The handler deadline ends when response headers are ready, so streamed bodies and upgraded WebSockets retain their own lifetimes. Foreground order, catalog and frozen-window reads reject exhausted read capacity with `429 capacity_exceeded`; the bounded live producers wait for capacity and cancel on release or shutdown. Subscription setup, request and send deadlines are 10, 30 and 5 seconds; heartbeat and idle timeouts are 15 and 35 seconds. Large outgoing messages are fragmented at the configured frame size, preserving one JSON message without buffering dozens of complete windows inside the socket library. Local query concurrency and retained views remain bounded by the actor layer. CORS and WebSocket handshakes share one canonical origin policy; configured origins are validated at bind time. Browser origins must match this application's host or be allowed with repeated `--cors-origin` or comma-separated `MARKET_CORS_ORIGINS`. Writer endpoints and raw authenticated hub forwarding are absent. Trusted ingestion services still connect directly to the hub.

`MarketRuntime` owns process startup, supervision and shutdown. Synchronization is an ordinary worker in `market-replica`: it owns the sole storage writer, commits batches and snapshot replacements, then publishes immutable views. The Telegram MTProto loop runs on its own supervised OS thread and Tokio runtime; its invocation scheduler shares that runtime. The `market-api` HTTP service is also supervised. Each starts once, and the application runtime stays outside the HTTP-worker factory.

Actors provide user-facing data access through one `MarketDataService` and a shared `MarketDataHandle` for API and bot callers. The service starts the data actors on its dedicated Actix thread and exposes the Arbiter and shared read executor so the application can start independent valuation actors: `OrderbooksActor` owns order, execution and freshness queries; `CatalogActor` owns gift collections, traits, book-directory projections, media resolution and catalog lookups; `MarketSubscriptionsActor` owns per-caller subscription leases and shared live-query feeds. Orderbook and catalog requests use separate mailboxes and one shared read budget provided by `market-replica::ReadExecutor`. Expensive reads run on tracked blocking workers. Portfolio floors use one ascending-price pass per collection over a pinned view, with preparation capacity acquired before the shared query budget. Catalog projections have a separate admission limit of up to four. Cancelled callers retain their blocking-work permits until that work finishes. Bot `/status` uses the orderbooks actor's status interface; the API maps internal status to public market availability.

Subscription leases own their shared feed directly. Dropping the final lease cancels its producer without a mailbox message; retaining a receiver alone does not keep it running. The actor keeps only weak lookup entries for reusable catalog watches and explicit ranges. Producers also stop when all receivers disappear. Completion releases feed capacity before publishing its terminal error, so immediate retries do not join a finished feed or wait for an obsolete lease to be dropped. Old leases cannot cancel a replacement feed. Read workers retain their separate permits until any cancelled blocking work exits.

Order watches preserve each caller's initial snapshot separately from coalesced shared updates, so a slow initial send cannot exceed the requested seed size. A joining seed can refresh an existing producer even while that producer is catching up. Publication uses the pinned read's internal observation clock to reject late results, including deletion of the final order in a book. The shared channel owns the latest state; producers recheck it after waiting for read admission and skip work already completed by a joining caller. Cancelled setup requests are checked again before registration.

Gift queries, orders, shared lookups, catalog entries and synchronization status are native Rust contracts owned by `market-gifts`. Valuation requests, reports, evidence and errors belong to `market-valuation`. Inventory portfolio valuation uses the shared batch engine; `market-portfolio` owns refresh orchestration and progress. The application starts the shared valuation service. Actors own query admission, replica reads, cached projections and data errors. `market-gifts-hub` translates gift queries into hub reads and interprets generic attributes, Telegram aliases, palettes and order targets as gift-domain values without depending on actors, replica storage or HTTP. Range and period invariants live beside the types in `market-gifts`; actor admission limits remain in `market-actors`. Valuation shares order projection rules, including normalized singleton model predicates, integer quantities and unsupported targets, while retaining one ascending-price scan per collection. Logical media references carry typed model/pattern identities; `market-api` presents them as thumbnail/animation URLs and namespaces content revisions for that HTTP representation. API serialization and HTTP error mapping remain in `market-api`. Catalog ETags are checked against domain revisions before building public DTOs or media URLs, so unchanged responses avoid that work. Collection and media path extractors deserialize domain IDs directly, using the same validation as JSON query IDs. The API and bot do not receive hub read messages, replica result objects or RPC error types through the data interface; shared native range states are published by the actors, and the API encodes per-watch snapshots and changes on tracked workers.

Each subscription call creates its own lease. Seeded order watches retain independent coverage; identical explicit ranges and catalog watches share computation. Dropping one lease leaves other callers subscribed. Dropping the last lease stops that feed and releases its capacity, even if an obsolete receiver remains. These are live connection subscriptions; saved preferences and durable alerts remain separate features.

The API and bot use `MarketDataHandle` directly; `market-api::MarketApi` forwards gift-domain queries and responses through that actor interface. The API and bot receive no storage writer. Within the API crate, WebSocket handlers receive a small `ConnectionSupervisor` that registers connection tasks and supplies a separate cancellation token for each connection. The application supervisor tracks the actor group, synchronization worker, bot and API service. The API drains its connection tasks, the actor group drains subscription producers, and the app-owned read runtime drains query workers. An API, replica or data-actor failure stops the application; bot failures and failed WebSocket connections remain isolated. Shutdown rejects new reads, cancels subscriptions, drains in-flight commits/reads, stops HTTP workers and joins the actor thread. Normal hub outages still use the synchronization worker's reconnect/rebuild loop.

The `best_bid` strategy uses the same `valuation.query`, `valuation.watch` and batch contracts, completed-report LRU and one-minute refresh checks. It has purpose `quote`, distinct from an estimate or reference. Query it with a selection, resolved gift or gift attributes; its typed data contains `best` and independent `references` for collection and known model, backdrop, model/backdrop and symbol. Each quote has `{value,order:{id,venue_id,quantity,expires_at?}}`, or `{error:{code,message,...}}` when no matching bid exists. All gift conditions must match; unknown facts do not satisfy restrictions. Selection quotes must cover every permitted combination, so a pair-only bid cannot inflate the model-only reference. Expired, nonpositive and exhausted bids are excluded. One bounded descending bid read is shared within a collection/currency batch; only winning quotes remain in reports. No Cartesian trait table or additional background refresh is created. Gift previews show the exact target's quote beside its estimate and conservative bid references beside Best asks, without treating bid quantity as a gift count. These observed quotes do not change the estimate formula. The `ask_floor` strategy ID stays unchanged; its display name is Best ask.

Valuation strategies implement `Strategy` with typed `Input` and `Output`. Selection inputs cover collections and trait/gift selections; execution inputs add a checked nonempty historical period; resolved-gift inputs preserve all available gift facts without requiring unused attributes. `gift_floor` uses the same registry and invocation path as ask floor and execution statistics. The coordinator resolves one target and supplies a read-only context with shared statistics. Mean/median cache entries include both selection and period, and discovery metadata comes from the registered input contracts.

Collection tiles abbreviate large floor prices (`1.23K`, `12.35M`) with exact decimal rounding; hover text retains the full quote. Listing cards show at most two fractional digits and append `..` when digits are hidden. Order details and price calculations retain exact values.

Valuation discovery exposes one capability descriptor: `input:{targets:["selection","gift"],period:"unsupported"}` (or `period:"required"` for execution strategies). The internal Rust input-contract names and redundant top-level capability flags are not public. Unused periods are rejected. Selection alternatives are sorted/deduplicated before cache lookup; empty criteria cover a collection, while symbols, model/backdrop combinations and gift-number bounds share the same selection format. REST and WS retain the same query/report; no legacy target aliases or omitted-symbol-map compatibility remain. Deploy frontend and backend together.

Successful valuation responses are encoded on four tracked blocking workers with cancellation checks and a shared 4 MiB response budget (`ApiLimits.response_bytes`). Oversized REST queries return HTTP 429; WS queries/watches return a terminal `capacity_exceeded` for that operation, leaving other operations connected. Encoded responses retain their serialization buffer as shared bytes through HTTP and WebSocket queues, avoiding a full-response copy. The encoder drains on shutdown. Request errors expose `{code,message}`; per-strategy failures use public computation codes and metric issues retain sample evidence. Internal storage errors and synthetic actor strategy identities are excluded.

Valuation reuse includes up to 32 weak entries for active-read sharing and a completed-report LRU holding at most eight distinct reads. Cache hits promote reports; inserting a ninth report evicts the least recently used cache owner. Reports have no retention TTL or periodic cache-cleanup task. The one-minute freshness deadline still controls dependency validation, including expiry for narrow indexed selections. A retained report must pass that validation before reuse after its deadline, so unchanged finite polls can reuse results even after long idle periods. Cached reports and collection/currency floor projections are held for at least 60 seconds. Changes, including listing expiry, are combined until that boundary; dependency checks then reuse unchanged prices or rebuild changed data once. Cached quotes may include asks that expired during the minute. Collection preparation uses one cache entry per collection/currency, holding a summary, optional trait statistics and one 60-second refresh deadline. The entry table is bounded to 512 books; only eight retain trait maps. Trait LRU eviction drops the maps while retaining the summary and deadline. Summary sweeps cannot promote trait recency or evict trait-bearing entries. Refreshing prepared traits also refreshes the summary in one scan; trait-only metadata changes preserve an unchanged summary and its calculation time. Statistics are immutable, and each cache read captures its deadline for the report. Later cache validation cannot move an existing report's timer. Cold selections calculate on demand, and bounded-cache eviction can require a new cold calculation. Unused collections are not periodically scanned. Identical requests share calculations; cancellation of one consumer does not cancel another. Dead weak entries are removed during cache access. Active watches keep independent ownership when their report leaves the completed LRU; replacing a query drops the superseded cache owner.

Open gift valuations refresh once after a recovered WS/market generation, without waiting for the minute interval. An in-flight request is never replayed; recovery uses a new operation ID, coalesces with work already preparing against that generation, and waits while the tab is hidden. Offline timers do not enqueue repeated reads. Valuation watches use the refresh timer and availability notifications, rather than reading on every order change. Availability changes update cached report status promptly without resetting its refresh deadline. Cancelling a pending watch read does not lose a due refresh. Unchanged periodic results advance the deadline without sending duplicate frames. Superseded hot query reads are released immediately; temporary per-strategy service failures retry within five seconds, while missing samples, unsupported targets and read-budget errors use the regular refresh interval. Encoder job registration is serialized with shutdown so drain cannot miss a newly registered job.

Valuation CPU regression benchmark: `cargo test -p market-valuation benchmark_preparation -- --ignored --nocapture`. The local debug fixture has 20,012 asks, 100 models, 100 backdrops and 10,000 observed combinations; no pair table is retained. Removing temporary attribute-map copies, singleton parsing vectors, quantity-formatting strings and duplicate gift-ID copies reduced median cold collection preparation from 213 ms to 179 ms, and independent-trait preparation from 268 ms to 234 ms (five runs per case). An exact two-ask pair read took 0.72 ms; cached unchanged-summary lookups averaged 2.1 µs each. After consolidating collection caches, a separate run of the same fixture measured 169 ms for cold summaries, 221 ms for traits and 0.4 µs per cached-summary lookup. These are local synthetic measurements, not production container CPU or heap measurements. The GUI computes each immutable trait payload's cache weight once; unrelated summary batches reuse it without serializing cached maps again. An in-flight selected-detail request owns that collection's summary slot during periodic sweeps. Older cached detail responses preserve the newer baseline and retry at the next scheduled minute, rather than immediately repeating the same request. Collection/currency switches and reconnects cancel superseded work before accepting replacements.

Internal order reads use one half-open range implementation. Local sorting is a typed `market_replica::Sort` in `ReadOptions`, alongside attribute matching; time/number ranking does not extend the hub proto. The adapter compiles gift scopes, while the actor/valuation callers choose local read policy. Both repositories carry the same wire contract. Range pages continue at `range.end` and retain frozen snapshot leases when requested; no internal navigation enum or redundant `next` field remains. Obsolete `Price` continuation aliases are rejected; clients holding those old private tokens must restart their read. Current compact order keys, storage/checkpoint formats and database index migration remain supported.

Batch valuation is available through `POST /valuations/batch` and WebSocket `valuation.batch`, with `{ "queries": [ /* ordinary ValuationQuery objects */ ] }` (1–100 entries). Normalized duplicate queries share lookup, computation and immutable report allocations while retaining their individual output slots. Results preserve input order and contain either `data` (the ordinary valuation response) or a typed `error` per item. Strategies, targets, currencies and execution periods use the same contracts as individual queries. Slug resolution reuses configured sessions with two lookups in flight. Market computation shares one pinned snapshot and collection contexts; repeated requested pairs reuse their read. Existing deadlines, cancellation, response budgets and one-minute floor-cache freshness apply. Portfolio inventories use this same batch engine internally, preserving progress and projecting only estimates rather than retaining full per-gift reports.

Collections, models, backdrops and symbols support native IDs and explicit alias selectors in the existing API. For example, an order query can use `"collection_id":"@slug:ResistanceDog"`, `"models":["@name:Dogfather"]` and `"backdrops":["@name:Black"]`. Omit the collection to filter backdrops/symbols across all collections in one globally sorted, paginated market view. Model aliases remain collection-scoped. Explicit slugs come from hub metadata; current names are convenient case-insensitive lookups, with model names scoped to their collection. Slugs are never invented from display names. Legacy source selectors remain supported by the adapter but are not advertised in catalogs. Unknown and ambiguous aliases are rejected. Orders, storage and media references retain native IDs.

The market GUI temporarily requires one collection and omits the All gifts option while cross-collection indexes are improved. Startup and older links without a collection choose the first available collection, preferring the current currency, before opening an order query or watch. Portfolio keeps All gifts and its shared backdrop/symbol choices from `/catalog`; it does not download all model catalogs. Selected collection choices retain their own rarity and floors; changing collections preserves shared trait selections and clears models. URLs prefer explicit slugs and unambiguous names. Portfolio All gifts uses the same picker data and selectors. Alias-filtered page versions bind the resolved selection as well as the inventory; clients continue with the first page’s version. Changed aliases restart visited coverage atomically without a Telegram inventory check. The bot accepts `/market collection=ResistanceDog model=Dogfather backdrop=Black symbol=Crown`, or `/market backdrop=Black` across collections. Bot market commands accept native IDs, `@slug:` and `@name:` references; source-specific `@tg:` and other legacy namespaces are rejected. Use percent encoding for spaces in command values, such as `model=Dark%20Knight`. It returns twelve orders in a three-column grid, with Previous/Next and an Open market link. Multiple alternatives and view controls use the readable grammar below; named command arguments remain supported.

Alias interpretation lives in the pure `market-gifts-hub::AliasCatalog` adapter. Alias indexes are rebuilt on metadata changes, with cancellation and membership/expansion budgets. Shared catalog lists use `Arc`s. Exact bids use collection-specific native predicates, and history merges one bounded head per collection rather than allocating a page for each. Hub protocol and persisted order identities are unchanged.

### Readable market links

The stateless `market-links` crate owns `MarketSelection` and the link codec, shared by bot commands and the generated GUI contract. This navigation model does not change REST or WebSocket query JSON. The GUI encodes attribute filters in `f`, for example (decoded for readability):

```text
?f=c=@slug:ResistanceDog|m=@name:Dogfather,@name:Rebellion|b=@name:Black|s=@name:Crown
```

`c` selects one collection; `m`, `b` and `s` select models, backdrops and symbols. Commas separate alternatives within a group, and `|` separates groups. Models require a collection; backdrop and symbol filters can span collections. `n=42` selects one gift number, and `n=10..200` selects a range (either bound may be omitted). Values accept native IDs, `@slug:` or `@name:` references. Percent-encode delimiters inside names before encoding the full query parameter: `@name:Vanilla%2C%20Jam`. URL builders handle both encoding layers.

Currency, venue, mode, bid matching, sort, price bounds, history period and an opened gift remain separate query parameters. An explicit `f=` means all attributes and takes precedence over legacy `collection` and JSON `filters` parameters. Existing URLs and `v_` Telegram launches remain readable. Invalid or repeated selection parameters fail rather than widening a selection.

The same grammar works in the bot:

```text
/market c=@slug:ResistanceDog|m=@name:Dogfather,@name:Rebellion|b=@name:Black
/market f=b=@name:Black|s=@name:Crown currency=XTR mode=bid bid_match=any
```

Small selections use Telegram's existing `startapp=v_…` payload. Larger selections use a complete website fragment (`/#f=…&currency=…`), preserving all selected filters without server storage, a link endpoint or an extra request. The GUI also switches long URLs to fragments, which are not sent in HTTP request lines. Oversized bot selections require `MARKET_PUBLIC_URL`; otherwise the command returns an explicit error rather than a default-view link.
