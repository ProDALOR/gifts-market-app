# Gifts Market App

A public React market browser with a Rust REST/WebSocket API and a persistent local read replica. Market Hub receives and validates authoritative facts. Each app instance synchronizes those facts once, then serves catalog, order and execution queries locally. Public requests never query the hub.

```text
Adapters → Market Hub ── snapshot + Watch ──→ App replica → REST / WebSocket → React
                          └───────────────→ Another app replica → more visitors
```

Each app process shares one replica across its HTTP workers. Current catalog, feeds and active-order indexes live in RAM. Execution payloads remain in local redb, with chronological, book and typed attribute indexes. Current entities are also persisted so a saved checkpoint always describes fully restorable state. There is no sibling Rust dependency: the copied `market-hub.proto` is the service boundary and the replica stores its generated messages directly.

Active orders belong to venue/collection/currency/side partitions, alongside their price, time and gift-number indexes. Ranked indexes share each partition's immutable order records. A global ordered location directory routes venue/order IDs to their current partition and preserves identity cursor ordering; catalog and feed records remain in a separate metadata map. Readers and revision tracking access both through `State` lookup and iteration methods. Same-partition replacements preserve location entries and remove only changed ranks. Snapshot views share unchanged partitions through copy-on-write. See the [partition-owned orders benchmark](docs/partition-owned-orders-benchmark.md) for measured read, update, allocation and memory tradeoffs. The database and cursor formats are unchanged.

## Run

Issue a service token on the hub with `market-hub token --id market-app`, then configure this application:

```sh
export MARKET_HUB_TOKEN='<issued service token>'
npm --prefix web ci
cargo build --locked -p market-media --bin market-media-render
npm --prefix web run build
cargo run --locked --bin market-app -- --hub-url http://127.0.0.1:50051 --data-dir data
```

Open `http://127.0.0.1:8080`. The interface provides collection search, separate quote currencies, unified or single-venue asks and bids, exact price/time/gift-number ordering, catalog trait filters, history and order details. Live scrolling replaces the active ordered-range watch in either direction while retaining visited rows. The grid mounts viewport rows plus overscan, keeps card heights stable, and preserves the visible order as range snapshots and atomic change batches arrive. Active range updates are coherent; cached regions refresh when revisited. Filters stay in the URL; asks, bids and history update live, and reconnect resumes around the visible order. Executions are confirmed facts from adapters; disappearing listings do not imply sales.

The service token stays on the server. Visitors need no hub credentials. Native configuration uses `MARKET_HUB_URL`, `MARKET_HUB_TOKEN`, `MARKET_HTTP_ADDR` and `MARKET_DATA_DIR`, or their CLI options. Every app instance needs its own data directory. It is bound to the source hub URL and service identity; use a new directory when connecting to a different source.

SVG generation builds with Cargo alone. For release deployment, build both binaries with `cargo build --release --locked -p market-app -p market-media --bin market-app --bin market-media-render --all-features` and deploy them together. Docker includes both automatically. A missing helper leaves thumbnails and TGS playback available.

For frontend development, start the Rust application and run `npm --prefix web run dev`. Vite proxies API and WebSocket traffic to port 8080. Rust serves `web/dist` normally; set `--web-dir` or `MARKET_WEB_DIR` for another location. Use `--no-web` or `MARKET_NO_WEB=true` to serve only the API, without frontend files or routes. Embedded `ApiConfig` defaults to `web_dir: None`; pass `Some(path)` to enable frontend hosting.

Deployment limits use `MARKET_HTTP_WORKERS` / `--http-workers` (default 2), `MARKET_MAX_CONCURRENT_QUERIES` / `--max-concurrent-queries` (32), and `MARKET_MAX_LIVE_QUERIES` / `--max-live-queries` (128). Live-query capacity counts producer tasks. Catalog watches and identical resolved order coverage share one live slot and retain independent leases. Order initialization has a separate bounded pool with the same live-query limit; joining an exact, current range skips initialization reads. These limits are separate from WebSocket connection limits. CLI flags take precedence over environment values. Native runs do not automatically load `.env`; export its settings before starting the process. Compose loads `.env` automatically.

Configuration migration: `MARKET_CORE_URL` / `--core` became `MARKET_HUB_URL` / `--hub-url`; `MARKET_NODE_TOKEN` / `--node-token` became `MARKET_HUB_TOKEN` / `--hub-token`; `--workers` became `--http-workers`; `--max-streams` became `--max-live-queries`. Remove `MARKET_TELEGRAM_BOT_ID` and `MARKET_TELEGRAM_BOT_USERNAME` from worker deployments. For Mini App-only deployments, replace them with `MARKET_MINIAPP_BOT_ID` and `MARKET_MINIAPP_BOT_USERNAME`. Old names are no longer read. Keep the same hub URL, issued token and data directory when migrating to preserve the replica binding.

## Synchronization and recovery

A new replica reads one consistent, unfiltered `Read(SNAPSHOT)` view, including catalog, current orders and execution history. It opens `Watch` at the first page's cursor immediately and spools changes to disk while loading snapshot pages. The hub renews the snapshot's idle lifetime as paging progresses. The app builds RAM indexes incrementally and replays staged changes before atomically publishing the completed replica. Orders, history and checkpoints become visible together.

Normal operation needs one authenticated Watch stream through a reusable gRPC channel. Each delivery commits its changes, execution indexes and checkpoint in one redb transaction before publishing the new RAM/history view. Execution upserts remove the same identity from active orders. Immutable execution retries are idempotent. Execution timestamps determine history order; the opaque Watch cursor determines replication progress, so late backfills are retained.

Internal entity kinds, order modes, sort order and index tags use validated enums. Entity and execution keys have named fields; numeric codes and tuple layouts are converted at the protocol, database and continuation boundaries. Existing databases and valid pagination tokens keep their original format.

After app restart, saved state is immediately available with delayed market availability. The app resumes Watch from its durable checkpoint. If the cursor expired or the hub restarted, it builds a replacement database while continuing to serve the previous copy. Completion swaps catalog, active orders and history together; facts absent from the replacement snapshot disappear too. An interrupted build is discarded on startup.

Market reads remain available during update delays. The connection-level `market.status` message reports `available`, `delayed` or `unavailable`, without storage or synchronization metadata. The GUI shows **Updates delayed** when fresh updates are interrupted. Valuations retain their calculation time and a `stale` flag; raw hub cursors and sync state are absent from public results and errors. `/readyz` still succeeds when saved market data can be served.

The local database is a rebuildable cache, not the authoritative archive. Stop this app and remove `replica.redb` and `building.redb` from its data directory to rebuild it. Preserve `session.key`, which signs user sessions independently of market replication. Never share a redb directory between running app instances. Disk usage includes execution history and, during a rebuild, the replacement database and its change journal.

## Docker

Copy `.env.example` to `.env` and set a reachable `MARKET_HUB_URL` and an issued `MARKET_HUB_TOKEN`. The app joins an existing Docker network named `market`; set `MARKET_NETWORK` in `.env` to use another network. The hub container must join the same network to be reachable by service name. If the hub is remote and you have no existing network, create it once with `docker network create market`. Start with:

```sh
docker compose config --quiet
docker compose up --build --detach
docker compose logs --follow --tail=100 market-app
```

Compose reads runtime configuration from `.env`; unset options use application defaults. Container data, bot, media and frontend paths are fixed to `/data`, `/bot-data`, `/data/media` and `/app/web/dist`, so native paths in `.env` do not override the mounted directories. Custom container paths require a Compose override with matching writable mounts. The listener is fixed to `0.0.0.0:8080`; `MARKET_APP_PORT` controls the published host port. After editing runtime settings, run `docker compose up --detach` to recreate the service with the updated environment.

Compose starts only this application, connects to the configured hub URL, publishes `0.0.0.0:8080` and persists its replica in `market-app-data:/data`. `MARKET_APP_PORT` changes the published port. Separate deployments use separate volumes. Multiple instances can sit behind a load balancer; retained snapshot pagination requires affinity to the instance holding the view. Query positions can move between instances synchronized to the same market.

For a hub running on a shared Docker network, configure `.env` with its service name and network:

```dotenv
MARKET_HUB_URL=http://market-hub:50051
MARKET_NETWORK=market
```

`MARKET_NETWORK` is used directly by `compose.yaml`; all deployments use the same `docker compose` commands. The network is external: Compose requires it to exist and leaves its lifecycle to the hub or administrator. When migrating from the former network override, use `docker compose up --detach` to recreate the app on the selected network. Existing data volumes are retained.

One Docker image includes the frontend, REST/WebSocket API, Telegram bot and Mini App support. A direct build uses `docker build -t market-app .`. The bot starts automatically when all three Telegram credentials are configured; serving the website and API requires none.

The image binds `0.0.0.0:8080`, stores the replica in `/data` and bot state in `/bot-data`, and runs as UID/GID 10001. Preserve both directories when running outside Compose. The image uses standard `SIGTERM` shutdown; Compose allows 15 seconds to drain workers.

The container becomes healthy when market data can be served, including saved data during an update outage. If it stays unhealthy, check `docker compose logs --tail=100 market-app` and `docker compose exec market-app curl --fail --silent --show-error http://127.0.0.1:8080/readyz`. Detailed synchronization and upstream retry diagnostics remain in application logs. `/healthz` checks the process; `/readyz` checks data availability. Both remain operational probes and are omitted from the consumer OpenAPI reference.

The Dockerfile has three stages: Rust compilation, frontend compilation and the final runtime image. The preview helper is built alongside the application; it requires no separate toolchain. A single `.dockerignore` excludes credentials, local state and generated assets from the build context. The frontend build generates public OpenAPI and TypeScript types before building React. Generated clients, dependencies and built assets are ignored. The Node build exports its schema using the compiled Rust binary.

## Gift previews and media

Model stills in listings, collection rows, trait choices and details prefer cached first-frame SVGs through native lazy `<img>` elements, including with reduced motion enabled. Telegram thumbnails remain a fallback for unavailable SVGs; symbol images use their supplied thumbnails. Only actual playback instantiates Lottie and downloads TGS in the browser. The thumbnail remains the fallback if SVG generation or image decoding fails, and temporary failures retry while visible. Cached SVGs remain available when their original TGS files are evicted, including after restart. Small animations use canvas where compatible; enlarged animations use SVG. The [preview comparison](docs/preview-benchmark.md) explains the size-dependent policy.

[SVG validation](docs/native-svg-validation.md) passes all 43 pinned real gifts with the pure Rust renderer. The [Rust exporter assessment](docs/rust-svg-alternatives.md) records the original comparison and the gradient, opacity and dash fixes that enabled migration. Original and generated media are never bundled.

The GUI uses a responsive orderbook. Below 960px, controls stack above a three-column gift grid. On desktop, a sticky sidebar fills the available viewport height, with a wider adaptive gift grid on the right. Currency sits beside IGIFTS in the header on both layouts. The desktop collection picker uses a scrollable list with full names and stable rows; it expands into spare sidebar space above stacked attribute filters. Mobile keeps the horizontal collection rail. Live updates run automatically; Pause and manual Refresh controls are omitted, while errors retain a Reload action. Both layouts share components and state; resizing preserves the visible gift, and sidebar scrolling does not load listing pages. On mobile, a floating, icon-only Back to top button appears after the controls scroll above the viewport. The reusable `BackToTop` component returns to the page start without resetting selections or loaded listings, respects reduced motion and Telegram safe areas, and hides on desktop or while a popup is open. Collections use shared search, media and selection state, multi-select Model/Backdrop/Symbol pickers and a virtual trait preview. Mobile collection labels refit to tile width and catalog renames; desktop rows use consistent typography. Dropdowns stay within the viewport and sidebar, changing direction as needed; scrolling their trigger out of view closes them. Order details use one keyboard-accessible dialog: a bottom sheet below 960px and a centered two-column layout on desktop, shared by asks, bids and history. Desktop dialogs fit their content within a bounded height. Artwork or bid alternatives stay on the left while price, attributes and valuation scroll in the right pane; the close button and venue action stay accessible on short screens. Resizing preserves the artwork and valuation state. The cover reserves a separate row for its collection name, grouped gift number and model name beneath the artwork, using the 18 symbol positions, scales and individual opacities from Telegram’s public gift SVG. The composition scales uniformly and crops to fit each pane. The information pane does not repeat the cover title. Currency, venue, Asks/Bids/History and Time/Gift #/Price sorting use the live API; currency and sort menus share keyboard navigation and outside dismissal, GRAM/Stars use vector symbols, and the MRKT mark comes from its public app assets; filters are restored from the URL. Infinite scrolling uses an atomic range watch; the server owns ordering and reconciliation. History uses the same live range subscriptions, including newly observed executions and late backfills within coverage. The preview appears only when traits are selected and shows only those selections. Model and backdrop rows balance their occupancy across the available width (twelve backdrops become six plus six). Models shrink from 52px to 40px, then 32px when needed to fit four rows; larger selections add rows at the minimum size. One continuous symbol layer uses a common tint and fixed tile spacing across every row. The footer stays at the viewport bottom on short pages and follows longer content. The layout adapts to Telegram safe areas and light/dark themes.

Collection prices have reserved space beside names in the desktop sidebar and below artwork or the selected name in the mobile rail; mobile search uses a taller tile to keep names and values separate. Model/backdrop picker chips place floors below their names beside the artwork, reserving the price line while values load. Compact chips wrap within the available width. Long names wrap and long values retain their exact amount in the tooltip. Neither layout creates per-option valuation requests. Run `npm --prefix web run test:attribute-values` for responsive placement, delayed-scope frames and batched request checks.

Criteria bids use compact rows of the same static model thumbnails, backdrop swatches and symbol icons as the trait pickers. Each row shows its first choice plus an overflow count. Unrestricted bids say “Any model”; unavailable catalog entries remain restricted. Bid cards show quantity and price, and details show every accepted alternative and gift-number range with a matching current-ask floor for the complete accepted selection. Detail artwork reuses the filter preview’s model grid and labels, with backdrop bands and symbols extending behind the collection name. Mobile bid covers fit their choices. Individual-gift estimates remain separate. Bid cards and condition chips stay static. Models in opened criteria and numbered-gift bids animate at detail priority through the shared adaptive playback budget, while background previews are suspended. Reduced motion and hidden tabs stop playback; closing details releases players. The budget admits 6, 10 or 18 simultaneous players according to CPU concurrency and available device memory, with a conservative default when resource hints are absent. Collection previews, selected traits, pointer interactions and details share capacity fairly; a large selection cannot consume every slot. Equal-priority queued models get four seconds of ready playback per turn, measured by a monotonic clock. Downloads do not consume that time, newly admitted players keep their own deadline, and unchanged winners keep playing when only a few replacements are waiting. Canceled leases ignore late readiness callbacks. Capacity changes release old grants before replacements, and resize alone does not recreate players. Hidden or fully suspended views do not keep rotation timers running.

Catalog media advertises `thumbnail_url` and, for models, `preview_url` and `animation_url`. Absent URLs are omitted. The GUI loads scalable model first frames through `GET /media/models/{catalog-option-id}/preview`; `GET /media/models/{catalog-option-id}/thumbnail` supplies fallback images. SVG responses use compression, weak ETags, conditional requests and a restrictive content security policy. Cached SVGs are validated against a small allowlist of passive vector elements and local paint references. The API resolves model document IDs through the catalog actor; clients cannot request arbitrary Telegram files. Thumbnail responses contain PNG, JPEG or WebP bytes; all media responses have content-type validation, ETags/304 responses and a one-day browser cache. Market JSON and WebSocket frames contain no image payloads or Telegram file credentials. Gift cards load SVG first frames lazily. Collection tiles and selected models request autoplay after remaining visible briefly; a shared budget admits at most six players, with interaction and details taking priority. Opening a detail or account sheet suspends background playback. Initial collection positioning skips animation downloads for intervening tiles; subsequent selection movement stays smooth. Download producers are queued and limited to four concurrent HTTP requests. Collection metadata loads are cached across visits and failed loads expose a retry action. Selected models use a flat balanced grid, so resizing preserves their media nodes. Canvas players resize their pixel buffers with their containers and release size observations when destroyed; placeholders, images and animations share card geometry. Order cards play on hover or focus. Animation requests share the same cache. Hovering or focusing an order card loads its TGS animation through `GET /media/models/{catalog-option-id}/animation`; order details play the animation automatically. Downloads and expression-free animation players are loaded only when needed. Small animations use canvas; enlarged artwork and gradients with independent transparency stops use SVG so smoke, glows and shadows remain transparent. Renderer selection is cached with the decoded data, and both renderers share the same download and playback budgets. The first animation frame fades over the still image in 120 ms. Leaving the preview immediately restores its static image and pauses playback; a 350 ms grace period reuses its renderer on quick re-entry. Scrolling offscreen, closing details, hiding the tab or enabling reduced motion releases the renderer immediately. Runtime player errors also restore the still image. Reduced-motion preferences show only static images and release all animation players. Unsupported or unavailable animations retain the still image; transient download failures retry while visible using shared cooldowns.

Media uses one typed route family, `GET /media/{kind}/{id}/{variant}`. `kind` is `models` or `patterns`; `variant` is `thumbnail`, `preview` or `animation`. Models support all three; patterns support thumbnails. Unknown categories/variants return 400, unsupported combinations or missing assets return 404, and temporary failures return 429/503 with `Retry-After`. The old unsuffixed thumbnail routes are removed. SVG variants support compression; thumbnails and validated TGS files are served without HTTP recompression. Catalog validators change with this URL/schema representation, so cached catalog data refreshes normally.

The GUI bundles gift and symbol silhouettes with CSS shimmer. They are available immediately and require no per-model outline requests, debounce timers or outline cache. Loaded artwork removes the placeholder; scrolling away or hiding the tab stops shimmer, and reduced motion keeps it static. Image failures keep a local silhouette while shared image recovery handles retry deadlines. SVG and fallback thumbnail retries are independent, and a recovered thumbnail stays visible until the preferred SVG decodes. Leaving the viewport, hiding the tab or changing artwork cancels recovery consumers. Remounted images check shared failure cooldowns before assigning a native image source. Animation recovery releases playback slots while waiting; renderer errors keep the still image until reactivation. Symbol completions and resize notifications share one canvas paint per frame. There is no remote placeholder endpoint or catalog field. Cards and details use the same Telegram-style 18-symbol composition; the attribute-selection banner retains its repeating layout.

The home mark uses the Columbus model from [Liberty Figure #11](https://t.me/nft/LibertyFigure-11). This fixed branding asset is bundled as a TGS plus a first-frame SVG generated by `market-media-render`. Only the header animates, sharing the existing playback budget, lazy player and visibility/motion rules; the footer uses the SVG. Both assets receive hashed build URLs and need no Telegram session or catalog lookup. These two curated branding files are exceptions to the runtime-media ignore rules in Git and Docker; downloaded market media remains excluded.

Gift previews compose the exact `tg.backdrop` and `tg.pattern` attributes around the model. Catalog backdrop metadata supplies the center/edge gradient colors and pattern tint; the selected pattern's transparent thumbnail is fetched from `GET /media/patterns/{catalog-option-id}/thumbnail` and repeated around the model. The background is painted once on a canvas and stays static during model playback. Pattern downloads are limited to visible previews, and the list does not load the animation player just to show patterns. Unknown or invalid palettes fall back to the ordinary model preview. Concrete gift cards and order details use the same composition, with a larger preview in details. Criteria bid cards reuse the picker's composition to show accepted alternatives: up to four static SVG models, backdrop bands and tiled symbols per trait, with overflow counts and complete conditions in details. Missing catalog entries remain marked unavailable; empty model constraints display “Any model”. Bid cards and details share trait resolution, preserving restricted IDs and cached names when catalog data is incomplete. Condition and picker chips reserve their artwork slots and mount native images on first visibility, retaining them for scroll-back reuse. Preview counts occupy a normal-flow footer; compact cards aggregate multi-trait counts with the breakdown in their labels, while expanded details keep per-trait counts.

Thumbnails and animations are downloaded, and SVG previews are generated, dynamically at runtime and are never committed or bundled into Docker images. `MARKET_MEDIA_DIR` / `--media-dir` selects the persistent disk cache; the default is `<MARKET_DATA_DIR>/media` (`/data/media` in Compose, on the replica volume). The bot’s shared grammers client downloads cache misses directly from Telegram. An instance without bot credentials serves existing cached files and can generate previews from cached TGS; missing original media returns 503. Use separate cache directories per writable node; never share the replica database directory between running instances. Custom container cache paths must be on a writable mounted volume. An uncached media asset also returns 503 while the Telegram connection is unavailable. Deleting the media directory safely rebuilds the cache on subsequent downloads.

An enabled bot worker shares its authenticated grammers client with the media downloader; no second Telegram login or update consumer is created. All media downloads and SVG generation are demand-driven; startup performs no warmup or prefetch. Cache entries and pending requests are keyed by document ID and media kind, so each variant is downloaded once and failures do not affect the other variant. The pending budget is 64 assets, with at most four concurrent downloads paced 75 ms apart. Download requests use a bounded FIFO queue; abandoned queued requests are skipped. Downloads time out after 15 seconds and callers after 30 seconds. Original compressed files are limited to 256 KiB; generated SVGs are capped at 1 MiB. Negative caching and Telegram flood-wait cooldowns prevent retry storms. A 16 MiB memory LRU with a five-minute TTL avoids repeated disk reads, hashing and TGS validation, including for conditional HTTP requests. Response bodies share the cached byte buffer. The disk cache evicts its least recently used files above 512 MiB; startup and background maintenance every minute remove recognized temporary files older than one hour and obsolete converter-version previews and retired numeric-ID `*.placeholder.svg` files. Unrelated files are preserved. Cold reads validate and decompress outside the directory index lock; atomic writes keep partial files out of responses. Directory scans run in the background, and shutdown drains tracked disk work and stops and reaps native child processes. Transport reconnects replace the media fetch connection together with the command connection; disk hits continue to work during outages.

The Telegram adapter coalesces document resolution across thumbnail and TGS misses, caches up to 128 private references for five minutes, and refreshes an expired file reference once. It downloads either a static thumbnail or the original `application/x-tgsticker` document. Model and pattern document IDs share the same cache without exposing Telegram download credentials. The cache stores `<document-id>.thumb` and `<document-id>.tgs` independently. First-frame SVGs use `<document-id>.preview-2-<source-sha256>.svg`, so changed TGS bytes or converter versions cannot reuse an old derivative. Preview requests coalesce after resolving the original TGS and share memory/disk quotas. Two rendering jobs run at most; each has a ten-second timeout. The converter runs out of process without Rust FFI, receives only validated local TGS/JSON, and has no Telegram credentials or download role. Last-consumer cancellation kills and reaps the child before releasing its conversion slot. TGS is validated as gzip-compressed vector animation JSON before storage: expanded JSON is capped at 2 MiB, with bounded dimensions/duration and no external assets or fonts. Expression metadata is discarded only from properties with baked values/keyframes, before caching and delivery; expression-only properties remain rejected. Ordinary TGS files retain their original bytes. The API serves validated compressed TGS bytes without `Content-Encoding: gzip`; the lazy frontend decoder expands them for the player. Both variants support ETags/304 and a one-day browser cache. Browser previews share pending downloads and one media failure policy. Missing or invalid assets are cached for 60 seconds; transient failures cool down for two seconds or the full server Retry-After. Cancellation and queue pressure are not cached as missing media. Failures use the same bounded resource retention as successes. Visible image recovery waits for retry deadlines without holding download slots, validates native decoding before remounting and stops when hidden or unmounted; a later visible use can retry expired failures. Animation data has a 16 MiB weighted cache; decoded pattern images and tinted frames each have a 2 MiB RGBA cache. Concurrent pattern requests share decoding and tinting. Each renderer gets its own copy of animation data. Visibility, motion and resize observation are pooled across previews. Offscreen backdrops release their canvas buffers and local tinted-frame references; selected backdrop color bands use CSS gradients. The transport-independent `market-media` crate owns disk caching and request coordination; `market-telegram-client` owns authenticated downloads, `market-api` owns catalog lookup and HTTP delivery, and `market-app` wires them together. API-only builds retain no Telegram dependencies.

Frontend code is organized into `web/src/collections`, `catalog`, `previews`, `orderbook` and shared `ui` modules. `GiftArtwork` renders resolved media; `GiftPreview` adapts market orders. All order kinds use `OrderDetails`, which owns background playback suspension for its lifetime. Attribute labels share catalog trait resolution, while pickers and details reuse `OptionArt` for visible static images and CSS backdrop swatches. Feature styles live beside their components, while `style.css` imports them and owns shared tokens and foundations.

Collection catalog choices expose optional typed `rarity`: `{"kind":"percentage","permille":5}` means exactly 0.5%; crafted traits use `{"kind":"uncommon"}`, `{"kind":"rare"}`, `{"kind":"epic"}` or `{"kind":"legendary"}`. Numeric values are integers from 0 to 1000. `market-gifts-hub` maps existing `rarity.permille` / `rarity.label` option metadata; missing or invalid metadata leaves rarity omitted. No hub protocol changes or extra Telegram calls are needed. Rarity changes participate in collection revisions and ETags.

Attribute pickers group exact percentages from rarest first, followed by craft tiers from Legendary to Uncommon and an Unknown group. Group controls show none, partial or full selection; a group click selects or clears its visible search matches while preserving other selections. Filters remain ordinary model/backdrop/pattern IDs, so REST and WebSocket query contracts are unchanged. Selection does not automatically expand when new catalog choices appear. Run `npm --prefix web run test:rarity` for responsive picker interaction regressions.

## Telegram Mini App and bot

Native Cargo builds keep Telegram support opt-in. Docker images include both `bot` and `miniapp` features; configuring all three Telegram credentials starts the worker automatically. Native builds without these features serve the market API and ordinary website without Telegram dependencies. Disabled features omit their CLI flags and subcommands; an API-only process ignores Telegram environment variables and creates no Telegram session or authentication storage.

| Cargo features on `market-app` | Included support |
| --- | --- |
| none (default) | Market API, WebSocket queries and ordinary website |
| `bot` | MTProto bot worker and `bot inspect` / `bot configure` commands |
| `miniapp` | Mini App launch settings, HTTP sign-in/session endpoints and `session-key` command |
| `bot,miniapp` | Both integrations |

`market-api` also exposes its own `miniapp` feature for embedding. The `bot` feature includes bot launch URL validation but does not enable Mini App HTTP routes. Compiling `bot` makes the worker available; configuring all three Telegram credentials starts it automatically.

```sh
# Default: market API and website, with no Telegram settings.
npm --prefix web run build
cargo run --locked -p market-app -- --data-dir data
# Mini App HTTP support without a bot worker:
MARKET_SCHEMA_FEATURES=miniapp npm --prefix web run build
cargo run --locked -p market-app --features miniapp -- --data-dir data
# Both integrations (set the runtime credentials described below):
cargo run --locked -p market-app --features bot,miniapp -- --data-dir data
```

Build the frontend against the same Mini App capability as the server. `MARKET_SCHEMA_FEATURES=miniapp` selects that capability when the frontend generates its schema through Cargo; with `MARKET_SCHEMA_BIN`, the provided binary's compiled features determine it. The browser build reads the schema and disables Telegram SDK initialization, sign-in requests and account controls when Mini App routes are absent.

Docker and Compose always build with `--all-features`. Bot startup is automatic when `TELEGRAM_BOT_TOKEN`, `TELEGRAM_API_ID` and `TELEGRAM_API_HASH` are all configured. Leave all three unset or blank to run without a bot; partial or invalid credentials fail startup with a configuration error. Native Cargo builds still support selecting features explicitly.

The same React interface works as an ordinary website and as a Telegram Mini App. The bridge loads only for Telegram launches, integrates safe areas and theme changes, and connects Telegram's Back button to order details, filters and the account menu. A small account control displays the server-verified identity. Market browsing stays public.

For a real Telegram launch, host the application at a public HTTPS origin. A deployment or HTTPS tunnel can forward to the existing HTTP listener. Configure these values in `.env` for Compose:

```dotenv
MARKET_PUBLIC_URL=https://markets.example.com
TELEGRAM_BOT_TOKEN=<BotFather token>
TELEGRAM_API_ID=<application ID from my.telegram.org>
TELEGRAM_API_HASH=<application hash from my.telegram.org>
```

`market-app` hosts one supervised bot worker when all three Telegram credentials are configured. It uses MTProto through grammers 0.12, logging in as the bot with its BotFather token and a Telegram application API ID/hash from [my.telegram.org](https://my.telegram.org). Supply these three credentials only to the application instance running the worker. Native runs read environment variables or CLI flags; Compose reads `.env`. Keep `.env` private; it is excluded from Git and Docker builds. These credentials and the saved MTProto authentication key are private and never part of public configuration or browser state.

Market operations are read-only. Orders require a collection and quote currency; omit venue to combine markets. Queries accept `source: "asks"` (default), `"bids"`, or `"history"`. Default sorts are ascending price for asks, descending price for bids, and newest execution first for history. Query size defaults to 100 (maximum 100). Trait selections use model, backdrop and pattern ID arrays; an empty array means any. Gift-number and price ranges are inclusive. At most 500 trait IDs may be selected in one query. Invalid IDs, negative or inexact decimal amounts, unknown query fields and inverted ranges are rejected.

The GUI shows padded Exact / Compatible buttons with matching semantics in tooltips. Exact is the GUI default and maps to `bid_match: "all"`; Compatible maps to `"any"`. Both choices are preserved explicitly in bid URLs. Bid queries accept `bid_match: "any"` (default) or `"all"`. Any requires overlap with the bid's accepted values in each selected model/backdrop/symbol group; unrestricted bid attributes accept any selection. All compares the complete bid conditions exactly: each selected trait set must equal the bid's accepted set, and an empty/omitted trait selection requires no restriction for that trait. Groups combine with AND. Gift-number ranges overlap under Any and require equal bounds under All, including open bounds; an omitted range requires no gift-number restriction under All. Equivalent singleton equality/set/range encodings match, and selection order and duplicates do not matter. Price bounds always filter the bid's price per gift. With no gift selections, Any shows all bids and All shows only unrestricted bids, subject to collection, currency, venue and price. Complex unsupported constraints remain visible only in unfiltered Any browsing. `bid_match: "all"` is rejected outside Bids.

For example, `{"source":"bids","bid_match":"all","filters":{"collection_id":"tg.gift.123","currency_id":"GRAM","models":["gold","silver"]}}` selects bids accepting exactly those two models with no backdrop, symbol or gift-number restrictions. Metadata may resolve from a retained expired ask; expired asks never supply valuation evidence. Criteria bids are excluded from gift lookup. Edition numbers and range bounds are positive JSON integers (`GiftNumber`); unknown gift numbers and traits remain nullable. Concrete gift orders must have quantity one and their collection must match the order book; criteria orders may have larger positive quantities. `GiftOrder` is an immutable domain value, built with `TryFrom<GiftOrderData>`; drafts can be edited, but consumers only receive checked orders. Construction requires execution time exactly for `executed` orders. The hub adapter also rejects execution lineage on active asks/bids. Observation can follow execution for historical backfills, so these timestamps are not forced into creation-time ordering. Native orders have no JSON/OpenAPI representation: presentation belongs to `OrderResponse`, shared by REST and WebSocket.

Gift valuation admits 32 concurrent requests with a thirty-second overall deadline. One supervised valuation actor serves API and bot callers, target estimators and batched current market values. A single ascending-ask pass prepares collection, model, backdrop and combination statistics on a tracked read worker. The cache retains up to eight collection/currency scopes with at most 20,000 aggregate/known-trait entries per scope. Dependencies are checked against the same pinned view used for gift lookup; unrelated catalog changes preserve cached statistics. Relevant dependency revisions, the earliest ask expiry and a five-minute safety age bound reuse. Rebuilds happen on demand; unchanged books need no periodic scan. Cache locks cover lookup/publication only, and bounded traversal identity sets are discarded before caching the aggregate counts. Cancellation propagates to queued and blocking work; the shared reader retains its permits until cancelled scans exit. Quantity-based portfolio floors remain a separate library capability and are not started by `market-app`.

Malformed input returns 400 `invalid_query`, unknown/unlisted gifts 404 `not_found`, saturation 429 `capacity_exceeded`, and lookup/service failures 503. Once a gift is resolved, the response is 200 even when metrics lack evidence. Per-metric errors use `not_enough_data`, `missing_trait`, `invalid_baseline` and `calculation_overflow`. Lookup, capacity and deadline failures remain request-level errors. Responses use `Cache-Control: no-store`.

Multiplier factors divide the selected trait's eligible ask floor by the collection floor in the same currency/snapshot. Each side requires three distinct identifiable gifts, while floors still consider all eligible listing rows. Counts do not measure distinct sellers or completed sales. Expired/exhausted listings, zero prices, unsupported targets, bids, executions and other currencies do not supply price evidence. Multipliers are displayed with two decimal places; final calculations use the original floors. This remains a floor-based heuristic: lowering only the collection floor increases the estimate. The embedded methodology explains this sensitivity; changing the estimator requires comparison against historical executions. Ask estimates exclude fees and do not represent confirmed sale proceeds.

Catalog responses (`GET /catalog` and `GET /collections/{id}`) contain catalog data without `cursor` or `sync`. The frontend consumes the shared connection-level `market.status` stream while browsing. Frozen and history reads do not open a socket solely for availability.

Collection and trait valuations use `POST /valuations/query` or WebSocket method `valuation.query`. Targets select what to value: `collection`, `model`, `backdrop`, `model_backdrop` or `gift`. Strategies select the calculation: `ask_floor`, `execution_mean`, `execution_median` or the existing `gift_floor` composite. `/valuations/strategies` advertises supported target kinds and `requires_period`. Strategies are explicitly selected; there is no server default. Strategy discovery includes an `input` kind (`selection`, `selection_with_execution_period`, or `resolved_gift`); supported targets and `requires_period` are derived from the same input contract used by runtime validation. `gift_floor` supports individual gifts through the same query interface.

```json
{
  "target": {"kind": "model", "collection_id": "tg.gift.123", "model_id": "model-from-catalog"},
  "currency_id": "GRAM",
  "strategies": ["ask_floor", "execution_mean", "execution_median"],
  "period": {"from": "2026-01-01T00:00:00Z", "until": "2026-02-01T00:00:00Z"}
}
```

Execution periods require inclusive `from` and exclusive `until` bounds and cannot end in the future. Mean weights each execution record equally, independently of quantity; median averages the two central prices for even counts. Collection/trait estimates require three records across three distinct gifts. Individual-gift execution estimates require three records for that gift. Evidence reports observed counts, distinct gifts, venues and first/last execution times. Available history is not asserted complete or seller-independent. Both execution methods share one traversal, capped at 50,000 matching observations. Missing evidence appears in price metrics; read failures and unsupported targets are independent strategy errors, preserving successful ask results.

One report coordinator validates target membership with direct catalog keys and evaluates all requested estimators on one admitted pinned snapshot. It shares the valuation service's floor cache, read budget, cancellation and supervised lifecycle. `Strategy::Input` and `Strategy::Output` stay typed. REST and WebSocket add strategy-owned display projections without exposing replica checkpoints. The GUI loads collection and trait floors automatically in gift details through the shared live subscription; there is no separate calculator or Calculate button. Gift estimates load when details open, and the info button reveals calculation fields and the guide. Execution-period strategies remain available through the public valuation API. The bot's `/value` command retains the individual-gift composite estimate.

Collection IDs, model IDs, backdrop IDs, pattern IDs, order IDs, venue IDs and currency IDs are distinct Rust types and serialize as strings. Model/pattern media references contain explicit thumbnail and optional animation URLs. Collections include an optional preview reference, so the collection picker needs no additional catalog request. The API does not expose Telegram access hashes or file references.

Sort is `price_asc`, `price_desc`, `time_asc`, `time_desc`, `number_asc`, `number_desc` or `identity`. Sorting applies to the full query before pagination. Active orders use observed time; history uses execution time. Missing gift numbers follow concrete numbers in ascending order and precede them in descending order. Ties use venue/order identity, with execution time also disambiguating history; descending reverses the complete key. History defaults to chronological identity order and accepts `period: {from, until}` with an inclusive start and exclusive end.

The frontend uses one initial bootstrap request and caches each selected collection’s details. Initial and reconnect revisions are compared with HTTP ETags, preserving valid cached data without polling. ## Queries, ranges and WebSockets

The GUI and external clients use one unversioned query API: `POST /orders/query` and WebSocket method `orders.query` share `GiftOrderQuery` and `OrderReadResponse`. All order operations use half-open `range:{start,end}` bounds, with null for an open head or tail. Queries default to at most 100 rows; the returned range end is the next page's inclusive start. Keys are reusable across filters with the same sort and source. Watches use the same flat query model: `orders.watch` reads up to `limit` rows, establishes their actual covered range atomically, and returns a snapshot with `range`. It then reconciles that fixed coverage with consecutive `orders.changed` batches. Later updates return complete coverage up to 100 rows or a capacity error. Snapshots always replace the subscribed state; gaps and reconnects start a fresh watch. No order revision, duplicate sort key, `next`, page token or per-watch sync frame is exposed. Finite WebSocket order results flatten `data`, `range` and optional `snapshot` at the envelope level, matching REST payloads.

Clients apply order changes atomically by removing deleted and replaced identities before merging the sorted upserts. The GUI builds each batch before committing its snapshot and lookup index, without depending on the internal structure of opaque ordering keys. The identity index keeps sparse updates efficient. Retired paging, sync, revision and reset fields are rejected by the frame validator.

Live `orders.snapshot` frames contain `type`, `id`, `sequence`, `data` and `range`; finite queries also support an optional frozen-view ID. Changes contain only sequence, upserts and removals. There is no operation-level connecting frame. `catalog.watch` returns `catalog.versions` manifests whose content versions match HTTP ETags, allowing clients to refresh changed catalogs without downloading unchanged entries on reconnect.

Ordering keys omit format-version markers and query fingerprints, retain sort/source validation and preserve exact lexicographic order with a compact encoding: packed decimal digits for prices, integer ranks for timestamps and gift numbers, and no rank payload for active identity ordering. A single byte packs sort/direction and source; history identity/time keys carry execution time once. REST and WebSocket ranges can reuse positions across filters; the supplied query determines all matching rows. Price positions are interpreted in that query's currency without conversion or validation of the original currency. This changes public navigation-key encoding without changing durable index formats. Deploy backend and frontend together, restart existing watches and discard old navigation keys.

Latest reads retain no view. Explicit snapshot reads preserve stable traversal during updates; `DELETE /orders/query` releases the lease. The GUI starts with one WebSocket watch that seeds 80 rows, queries additional pages as needed, retains visited listings, watches viewport coverage with headroom below the 100-row cap, and preserves scroll anchors. Asks, bids and history share one query type, including execution-period filters. The controller tracks covered intervals separately from cached rows: a limited reconnect baseline retains older rows and marks the interval before the retained tail unread. Bounded queries fill gaps without rereading the whole cache or declaring pagination complete too early. Viewport watches stay within contiguous covered intervals.

Pagination waits for a live baseline after reconnecting; an outstanding page is canceled and its intent resumes against current unread coverage. Empty filtered pages continue scanning, while transient failures respect backoff. Typed watch state and market availability jointly determine status, so an available market cannot mark an errored or reconnecting subscription Live. Subscription retries use socket-owned backoff and the latest visible anchor. Delayed pages cannot overwrite newer watched rows; collection changes close the old feed before layout callbacks run. Explicit frozen reads rebuild through the visited tail, including gaps, before publishing a replacement snapshot. Read, scan, memory and outgoing-byte budgets remain enforced. See [the WebSocket protocol](crates/market-api/src/websocket/protocol.md) for complete navigation, snapshot, status and cancellation semantics.

Ranked ask queries use per-partition enum memberships for selective model, backdrop and symbol filters. Reads choose the smallest matching trait group, reuse the authoritative shared order records and apply the remaining filters before returning results. This avoids exhausting the 10,000-candidate scan budget on unrelated listings when refreshing a sparse live range. Memberships follow order updates and removals, survive pinned reads through copy-on-write and rebuild from stored orders at startup. Candidate preparation remains bounded; bid constraints retain their separate Any/All matching semantics. No storage or protocol migration is needed.

API errors use `{error:{code,message}}`, including JSON, query/path extraction and framework errors. Invalid parameters return 400, oversized JSON returns 413, unsupported content types return 415, unknown routes return 404 and unsupported methods return 405. JSON query bodies are limited to 64 KiB by default. The same extractor policy is installed by the public route configurator and the full server.

WebSockets reserve operation IDs during asynchronous setup, so pings, cancellation and shutdown remain responsive. `cancel` stops a request or subscription. Validation failures with a valid unused ID return a correlated terminal `error`. Reusing an active ID or sending a command without a valid ID produces nonterminal `command_error`, preserving active work; only the latter has an empty ID. Connection failures use WebSocket close frames. Socket writes are polled concurrently with commands and operation jobs, so backpressure cannot block cancellation. An internal generation filters queued frames and late completions, while clients use fresh wire IDs to ignore frames already sent for canceled operations. The browser uses the socket's native connection state, bounds handshakes to ten seconds and detaches callbacks and timers on close. Reconnect restores subscriptions without replaying one-shot requests; unchanged query updates preserve their local snapshot and sequence. An oversized page produces a terminal subscription error and releases the ID. Slow consumers close with code 1013 so clients can reconnect and resubscribe. Order snapshots and change batches encode on four tracked blocking workers and enforce the output limit while writing. Shutdown drains encoding jobs after closing connections.

`ApiLimits` and `WebSocketLimits` centralize service bounds. Defaults are 256 WebSocket connections across HTTP workers, 16 pending/active subscriptions and eight requests per socket, 64 KiB input messages, 4 MiB encoded order responses, and an outgoing application queue bounded to eight messages and 8 MiB. The HTTP request-head receive timeout and extraction/handler deadline are both 10 seconds; exceeding the handler deadline returns a structured `503 timed_out` error. The handler deadline ends when response headers are ready, so streamed bodies and upgraded WebSockets retain their own lifetimes. Foreground order, catalog and frozen-window reads reject exhausted read capacity with `429 capacity_exceeded`; the bounded live producers wait for capacity and cancel on release or shutdown. Subscription setup, request and send deadlines are 10, 30 and 5 seconds; heartbeat and idle timeouts are 15 and 35 seconds. Large outgoing messages are fragmented at the configured frame size, preserving one JSON message without buffering dozens of complete windows inside the socket library. Local query concurrency and retained views remain bounded by the actor layer. CORS and WebSocket handshakes share one canonical origin policy; configured origins are validated at bind time. Browser origins must match this application's host or be allowed with repeated `--cors-origin` or comma-separated `MARKET_CORS_ORIGINS`. Writer endpoints and raw authenticated hub forwarding are absent. Trusted ingestion services still connect directly to the hub.

`MarketRuntime` owns process startup, supervision and shutdown. Synchronization is an ordinary worker in `market-replica`: it owns the sole storage writer, commits batches and snapshot replacements, then publishes immutable views. The Telegram MTProto loop and the `market-api` HTTP service are also supervised workers. Each starts once, and the application runtime stays outside the HTTP-worker factory.

Actors provide user-facing data access through one `MarketDataService` and a shared `MarketDataHandle` for API and bot callers. The service starts the data actors on its dedicated Actix thread and exposes the Arbiter and shared read executor so the application can start independent valuation actors: `OrderbooksActor` owns order, execution and freshness queries; `CatalogActor` owns gift collections, traits, book-directory projections, media resolution and catalog lookups; `MarketSubscriptionsActor` owns per-caller subscription leases and shared live-query feeds. Orderbook and catalog requests use separate mailboxes and one shared read budget provided by `market-replica::ReadExecutor`. Expensive reads run on tracked blocking workers. Portfolio floors use one ascending-price pass per collection over a pinned view, with one valuation slot acquired before the shared query budget. Catalog projections have a separate admission limit of up to four. Cancelled callers retain their blocking-work permits until that work finishes. Bot `/status` uses the orderbooks actor's status interface; the API maps internal status to public market availability.

Subscription leases own their shared feed directly. Dropping the final lease cancels its producer without a mailbox message; retaining a receiver alone does not keep it running. The actor keeps only weak lookup entries for reusable catalog watches and explicit ranges. Producers also stop when all receivers disappear. Completion releases feed capacity before publishing its terminal error, so immediate retries do not join a finished feed or wait for an obsolete lease to be dropped. Old leases cannot cancel a replacement feed. Read workers retain their separate permits until any cancelled blocking work exits.

Order watches preserve each caller's initial snapshot separately from coalesced shared updates, so a slow initial send cannot exceed the requested seed size. A joining seed can refresh an existing producer even while that producer is catching up. Publication uses the pinned read's internal observation clock to reject late results, including deletion of the final order in a book. The shared channel owns the latest state; producers recheck it after waiting for read admission and skip work already completed by a joining caller. Cancelled setup requests are checked again before registration.

Gift queries, orders, shared lookups, catalog entries and synchronization status are native Rust contracts owned by `market-gifts`. Valuation requests, reports, evidence and errors belong to `market-valuation`. Quantity-based portfolio floor actors are opt-in through its `portfolio` feature, enabled by `market-portfolio`; the application starts the shared valuation service. Inventory support remains available for upcoming user portfolio calculations. Actors own query admission, replica reads, cached projections and data errors. `market-gifts-hub` translates gift queries into hub reads and interprets generic attributes, Telegram aliases, palettes and order targets as gift-domain values without depending on actors, replica storage or HTTP. Range and period invariants live beside the types in `market-gifts`; actor admission limits remain in `market-actors`. Valuation shares order projection rules, including normalized singleton model predicates, integer quantities and unsupported targets, while retaining one ascending-price scan per collection. Logical media references carry typed model/pattern identities; `market-api` presents them as thumbnail/animation URLs and namespaces content revisions for that HTTP representation. API serialization and HTTP error mapping remain in `market-api`. Catalog ETags are checked against domain revisions before building public DTOs or media URLs, so unchanged responses avoid that work. Collection and media path extractors deserialize domain IDs directly, using the same validation as JSON query IDs. The API and bot do not receive hub read messages, replica result objects or RPC error types through the data interface; shared native range states are published by the actors, and the API encodes per-watch snapshots and changes on tracked workers.

Each subscription call creates its own lease. Seeded order watches retain independent coverage; identical explicit ranges and catalog watches share computation. Dropping one lease leaves other callers subscribed. Dropping the last lease stops that feed and releases its capacity, even if an obsolete receiver remains. These are live connection subscriptions; saved preferences and durable alerts remain separate features.

The API and bot use `MarketDataHandle` directly; `market-api::MarketApi` forwards gift-domain queries and responses through that actor interface. The API and bot receive no storage writer. Within the API crate, WebSocket handlers receive a small `ConnectionSupervisor` that registers connection tasks and supplies a separate cancellation token for each connection. The application supervisor tracks the actor group, synchronization worker, bot and API service. The API drains its connection tasks, the actor group drains subscription producers, and the app-owned read runtime drains query workers. An API, replica or data-actor failure stops the application; bot failures and failed WebSocket connections remain isolated. Shutdown rejects new reads, cancels subscriptions, drains in-flight commits/reads, stops HTTP workers and joins the actor thread. Normal hub outages still use the synchronization worker's reconnect/rebuild loop.

Performance measurements and repeatable commands are in [the ordered-query benchmark](docs/ordered-query-benchmark.md).

Tests cover snapshot/Watch overlap, durable checkpoint recovery, replaced datasets, exact prices, typed duplicate list matching, chronological backfills and local-only public reads. The integration check starts a disposable real hub, a fixture built from this repository’s protocol bindings, and the app on random local ports. No adapter checkout is needed or modified. The harness builds the frontend from the selected app binary’s schema, so API-only and Mini App capabilities stay matched. Child environments discard inherited market/Telegram settings and credentials; the test supplies its own local token and temporary storage. It verifies browser layouts, live updates, execution transitions, hub restart rebuilds and persisted reads while the hub is offline. It never opens account exports or contacts markets. Install its browser with `cd web && npx playwright install chromium`. Optional `--keep target/replica-preview` retains a synthetic preview; use a fresh directory.

The disposable smoke run uses `scripts/range-probe.mjs` to verify range coverage, frozen navigation, snapshot release and resume; it sends no legacy WebSocket page commands. The same probe can run against the supervised API fixture with `cargo test --locked --offline -p market-api --test market_api range_watch_smoke_probe_uses_portable_positions_and_frozen_leases -- --ignored`. It requires Node.js 24.

Copy coordinated contract updates into the client repositories and use the hub's `scripts/check-contracts.py` before release. All builds use only their own repository. No legacy gateway routes or copied hub implementation crates remain.


Gift details use one price/estimate panel and an aligned ask-floor table in this order: collection, model & backdrop, model, backdrop, symbol. Floors show rounded amounts and unique gift counts, with exact prices and listing counts in tooltips. Symbol floors are calculated by the same bounded catalog projection and refresh with the selected collection; they remain independent of the gift-floor estimate formula. All compatible strategies appear in one column, without a strategy selector, and share one batched valuation request. Open details refresh automatically once per minute, without manual refresh controls or stale-text warnings. Refreshes never overlap; hidden tabs pause and catch up once when visible, and closing or changing gifts cancels pending work. Each row has its own result, freshness, price comparison and lazy calculation guide, driven by discovered metadata and typed display fields. Collection artwork reuses its default preview (or the local gift placeholder), while the model/backdrop icon combines the static model image with its backdrop swatch.

Valuation strategies implement `Strategy` with typed `Input` and `Output`. Selection inputs cover collections and trait/gift selections; execution inputs add a checked nonempty historical period; resolved-gift inputs preserve all available gift facts without requiring unused attributes. `gift_floor` uses the same registry and invocation path as ask floor and execution statistics. The coordinator resolves one target and supplies a read-only context with shared statistics. Mean/median cache entries include both selection and period, and discovery metadata comes from the registered input contracts.
